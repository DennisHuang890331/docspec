# 第二期架構：軟體領域（取代 OpenSpec）

- 狀態：架構草案，**等使用者確認（第二期架構關卡）**
- 依據：`docs/dev/system-design.md` 架構第二版、第一期（已驗收，2026/09/30）
- 最後更新：2026/09/30
- 第二期要滿足的系統需求：SR7（延伸到軟體）、SR8（任務）、SR9（軟體）、SR10、SR12、SR13、SR15（軟體）、SR19、SR20（OpenSpec 匯入）。

---

## 1. 目標與範圍

**目標**：你的專案可以停用 OpenSpec，軟體的規格、變更、任務、驗證全部在 docspec 裡完成，而且修好使用意見裡 OpenSpec 的問題：
- 設計決策會蒸發
- 格式檢查抓不到矛盾
- 修改需求要整段重抄
- change 長到失控
- 任務沒有多 agent 需要的欄位

### 1.1 OpenSpec 功能對等清單（SR19）

**要對等的**：你實際在用的功能，加上 OpenSpec 的核心功能。

- 能力規格（capability → requirement → scenario），代表「目前系統的行為」。
- change 的生命週期：
  - 提案（為什麼、改什麼、影響哪些能力）
  - 規格差異
  - 設計
  - 任務
  - 實作
  - 驗證
  - 封存（把差異併回規格）
- 同步規格：不封存，只把差異併回規格（OpenSpec 的 sync）。
- 探索：動手前先討論。這部分直接沿用現有的 explorations/ 與治理層的問題紀錄，不另做。
- 修改進行中的 change，並保持各部分一致（OpenSpec 的 update-change）。
- 驗證格式與一致性（validate）、列出與查看（list、show）。
- 專案背景與規則注入（OpenSpec config 的 context、rules）。
- 各家 agent 的 skill 安裝（第一期之前已完成）。

**不做的**：

- OpenSpec 的 store、workset、多 repo 規劃。這些功能在 OpenSpec 自己那邊也還在實驗、方向未定，不是你在用的。
- 自訂 schema。
- onboard、feedback、shell 補完、使用統計。

## 3. 資料模型（YAML，一筆一檔）

### 3.1 能力規格：`docspec/software/specs/<能力>.yaml`

代表「目前系統的行為」，只能由 change 封存或同步時改動。

- **目的**：一兩句話。
- **需求**：
  - 編號：能力內唯一，例如 `task-entry-page/R3`
  - 標題
  - 規範句：SHALL／MUST
  - 驗證方法：測試、展示、檢查、分析（SR12）
  - 依據的治理決策（可選）
- **情境**：屬於某條需求。
  - 編號，例如 `task-entry-page/R3/S2`
  - 標題
  - WHEN／THEN

### 3.2 軟體 change：`docspec/software/changes/<change>.yaml`

一個 change 一個檔。

- **提案**：
  - 為什麼要改
  - 改什麼
  - 影響哪些能力
  - 影響哪些程式區塊（repo 與路徑）
- **規格差異**：以需求和情境的編號為單位。
  - 動作分為新增、修改、移除、改名。
  - **可以只改某一個情境**，沒改到的不用重抄。
  - 每一筆修改都記錄「基準指紋」，也就是修改時那條需求的內容指紋。封存時如果規格已經被別的 change 改過，指紋對不上，就停下來請人處理，不會靜默覆蓋（SR11）。
- **設計**：
  - 背景、目標與非目標、風險、遷移計畫，用 YAML 的多行文字存放。
  - **設計決策不存在這裡**，改成治理層的決策紀錄（見第 4 節）。
- **任務**：
  - 實作哪些需求
  - 預計改哪些檔案（repo 與路徑）
  - 驗證方式
  - 證據
  - 狀態
- **前後依賴**：先做哪些 change（dependsOn）。

**給人讀的版本**：由工具輸出成 Markdown，用在 PR 審查和給你看。

### 3.3 證據：隨任務記錄

- **型別**（SR12）：
  - 測試執行：指令、commit、環境、通過／略過／失敗數。略過視為失敗，除非事先聲明。
  - 截圖審核：畫面尺寸、看了什麼、結論。
  - 真模型執行：模型版本、測試資料、執行前後檢查的不變量。
  - 量測：數值對門檻。
  - 使用者驗收：用第一期的「對話中覆述確認」記錄你的回覆。
  - 豁免：依據哪條裁定、什麼情況下重新打開。
- **規則**：任務要有符合其驗證方式的證據，才能標成完成。

## 4. 關鍵設計選擇

1. **軟體設計決策併入治理層的決策紀錄**。
   - OpenSpec 的 design.md 決策在 change 封存後就蒸發，這是你使用意見第一點的根源。
   - 做法：change 的設計決策直接建成治理層的決策，標明屬於哪個 change。這樣可以直接沿用第一期的機制：取代要寫完整新版、依據裁定、影響分析、目前有效設計。
   - 結果：D7 → D15 這種狀況，在軟體領域一樣用同一套方式處理。
2. **任務是追溯鏈的最後一段**（第一期已裁定「丙」）。
   - 鏈結為：需求 ← 任務 → 檔案／測試。
   - 決策被取代時，影響分析沿著這條鏈一路列到任務和測試。已完成的任務標為「需重看」，不會重新打開。
3. **程式碼不進 docspec 的暫存區**。
   - git 分支本身就是暫存區；change 只記錄實際改到的 commit。
4. **多 repo**。
   - 在設定裡登記程式所在的 repo，例如 `labelvault: tools/labelvault`。
   - 檔案與證據一律寫成「repo:路徑@commit」。
   - 工作區本身沒有 git 也能運作。
5. **專案基線**（SR10）。
   - 封存或發布時，記下當下的文件版本、規格狀態和各 repo 的 commit。
   - 這樣可以回答「文件第三版描述的是哪個規格、哪個 commit」。
6. **change 過大提醒**（使用意見 OpenSpec 第 4 點）。
   - 任務數超過門檻，或新增的決策影響到 change 宣告範圍以外的能力時，工具提示拆成新的 change。這只是提示，不擋。
7. **文件章節可以 realizes 軟體需求或軟體 change**。
   - 需求被修改，或 change 封存時，對應的章節轉為過時。
   - 這直接解決「程式做完、文件要人記得回來改」的問題。

## 5. 流程與 skill

**流程**：探索（沿用）→ 提案 → 實作 → 驗證 → 封存

**skill**（照 OpenSpec 精簡的做法）：

- `dspx-propose`：建立 change，寫出提案、規格差異、設計，並拆出任務。設計決策建成治理決策，依據你的裁定。
- `dspx-implement`：逐項做任務。宣告要改的檔案，產生證據後才勾完成。
- `dspx-verify`：檢查完整性（任務與證據）、正確性（需求與情境的覆蓋）、一致性（有沒有違反有效決策）。這是建議性質，只標出問題，不擋。
- 封存用指令完成（`archive`）：差異併回規格、基準指紋檢查、記錄專案基線、roadmap 自動推導為完成、相關文件章節轉為過時。

## 6. OpenSpec 匯入（SR20）

- **讀取來源**：
  - `openspec/specs/**/spec.md`
  - `openspec/changes/<進行中>/`
  - `openspec/changes/archive/`
- **轉換方式**：
  - Markdown 的 Requirement／Scenario 轉成有編號的 YAML。
  - 進行中的 change 轉成軟體 change，包含提案、差異、任務與勾選狀態。
  - 已封存的 change 轉成歷史紀錄。
- **design.md 的決策**：匯入成治理層決策。
  - 原文裡寫著「與前文衝突時以此為準」的局部取代，工具無法自動合併。這類決策匯入後標為「待合併」，列進待處理清單，由 agent 寫出完整新版、經你確認後才生效（依第一期裁定）。
- **匯入後的驗證**：用 `docspec check` 驗證，並列出匯入報告，說明轉了多少、哪些需要人工處理。

## 7. 驗收情境（以台中港專案資料為準，資料只在本機，不進 repo）

- **S5 豁免**：dataset-library 封存時未驗證的三項（車輛 bag、NAS、資料碟）以豁免證據呈現；roadmap 顯示「完成（含豁免三項）」。
- **S2 完整鏈**：取代「/tasks 頁面維持不變」這條決策時，系統把以下項目全部標為可疑：
  - 舊規格中「第一列任務在第一畫面」這條需求
  - 已完成的任務 6.6（需重看）
  - 瀏覽器測試 test_entry_page.py
  - 說明書相關章節
- **S7 匯入**：
  - 7 份規格、28 個已封存 change、進行中的 dataset-library 全部匯入，`check` 通過。
  - 需求與情境數量和原檔一致。
  - D7／D13／D15 列為待合併。
- **S8 只改一個情境**：修改一條需求的單一情境時不用重抄其他情境；封存後其他情境原封不動。
- **S9 並行衝突**：兩個 change 修改同一條需求，後封存的那一個因基準指紋不符而停下，不會靜默覆蓋。

## 8. 需要使用者確認的事（架構層）

1. 軟體 change 的設計決策是否併入治理層的決策紀錄（第 4 節第 1 點）？
2. 功能對等清單的範圍（第 1.1 節）：不做 store、workset、自訂 schema，可以嗎？
3. 你對一個 change 的「驗收」是否需要記錄？
   - 建議：只有驗證方法是「展示」或「檢查」的需求（例如介面截圖）才需要你的驗收，其他以測試證據為準。
4. 指令與 skill 的命名：
   - 建議指令放在 `docspec code …` 底下（`docspec code spec`、`docspec code change`、`docspec code task`、`docspec code archive`），和現有的文件 change 指令分開，避免混淆。
   - skill 叫 `dspx-propose`、`dspx-implement`、`dspx-verify`。
