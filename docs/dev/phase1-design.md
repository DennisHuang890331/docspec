## 2. 紀錄儲存

### 2.1 目錄

```
docspec/
├─ governance/                  ← 新增：治理層
│  ├─ questions/<id>.yaml       待裁定問題，一筆一檔
│  ├─ rulings/<id>.yaml         裁定
│  ├─ decisions/<id>.yaml       決策
│  ├─ roadmap/<id>.yaml         里程碑與工作項目
│  ├─ suspects/<id>.yaml        可疑標記
│  └─ authority.yaml            權限表
├─ corpus/ changes/ glossary.yaml writing-guide.md   ← 文件領域（不動）
└─ config.yaml
```

- **一筆一檔**：兩個分支各自新增紀錄時，只會多出不同的檔案，git 合併不會衝突（SR11）。
- **每個檔案各自封條**：沿用現有的封條機制（`engine/sealed.py`），手改會被偵測。因為一筆一檔，合併時不會有兩個分支同時改同一個封條的問題。
- **舊的 roadmap 檔**（每份文件一份，加上一份跨文件的）由轉換指令搬進 `governance/roadmap/`；轉換前的舊檔在一個版本內仍可讀。

### 2.2 編號（2026/09/29 裁定）

- 格式為「類別＋工具前綴＋流水號」，例如決策 `D-claude-13`、裁定 `RL-gpt-4`、問題 `Q-gemini-2`、工作項目 `W-claude-21`、里程碑 `M-claude-3`。由使用者本人在終端機建立的，前綴為 `user`。
- 每個前綴有自己的流水號，因此不同工具同時編號不會撞號。
- 工具前綴由引擎自動判斷：依各家 agent 執行環境的環境變數判斷，判斷不出來時必須用 `--by` 指定。
- 剩餘風險：同一個工具在兩個分支同時編號，仍可能撞號。處理方式是合併後由 `check` 偵測重複編號，並提供重新編號指令，把後建立的那一筆改號，同時更新所有引用它的地方。
- 給使用者看的內容一律以標題為主，編號只放在括號裡。
- 引用時加命名空間，例如 `gov:D-claude-13`，避免和文件內自由命名的決策編號撞名。

## 3. 紀錄型別

### 3.1 待裁定問題

- **欄位**：標題、白話說明、提出者、提出日期、影響哪些紀錄、狀態。
- **狀態**：
  - 待裁定
  - 待解釋（使用者表示沒聽懂）
  - 已裁定（連到回答它的裁定）
  - 撤回

### 3.2 裁定

- **欄位**：
  - 使用者原話
  - 日期
  - 轉記者（哪個 agent）
  - agent 的解讀
  - 回答哪些問題
  - 是否暫定
  - 取代哪些舊裁定
  - 狀態
- **狀態流轉**：
  - 待確認 → 已確認：只有使用者能做，見第 4 節。
  - 待確認 → 駁回：使用者表示轉記錯了。
  - 已確認 → 被取代：新裁定明確宣告取代它。
- 一條裁定可以回答多個問題、影響多條決策。

### 3.3 決策

- **欄位**：標題、**完整的現行內容**、理由、依據哪些裁定、取代哪些舊決策、狀態。
- **狀態流轉**：
  - 草稿 → 有效：前提是依據的裁定全部已確認（驗收情境 S3）。
  - 有效 → 被取代：由新決策宣告取代。
- **取代規則**：新決策必須寫出合併後的完整內容。舊決策原文保留，只改狀態。

### 3.4 Roadmap

- **里程碑欄位**：標題、類型（計畫查核點或交付物）、可選的目標日期。
- **工作項目欄位**：
  - 標題
  - 屬於哪個里程碑
  - 上層項目
  - 前置項目
  - 指向哪些文件或 change
  - 豁免：附裁定，並說明什麼條件下取消豁免
- **狀態由系統推導**，不手寫：
  - 未開始
  - 進行中
  - 卡住（前置項目未完成，或有未處理的可疑標記）
  - 完成
  - 完成（含豁免）
- 做完的項目保留在檔案裡，不再移出。這是和現行 docspec 最大的語意差異。

### 3.5 可疑標記

- **欄位**：觸發事件（哪條紀錄被取代或駁回）、受影響的項目、傳遞路徑、狀態（未處理或已清除）、清除理由、清除者。
- 已完成的工作項目被標記時，狀態顯示「需重看」，不會回到未完成。

### 3.6 權限表

- 第一期只強制「哪些動作需要使用者批准」。
- 預設需要使用者批准的動作：
  - 確認或駁回會改變決策的裁定
  - 發布文件：agent 完成檢查與預覽後送出發布申請，使用者批准後才由工具執行（2026/09/29 裁定）
- 可以在設定裡加上更多動作，例如封存文件 change。
- 一般性的小裁定不需要批准，但在清單上標示「未經本人確認」，而且不能作為決策生效的依據。
- 註：現在設定檔裡的「發布必須由人觸發」（`autonomy.publish: human`）只是一個標示，程式並沒有強制。第一期會真正強制。

## 4. 「只有使用者能做」如何保證

引擎無法得知指令是誰下的，所以採三層防護：

1. **hook 攔截**：四家 agent 的防護都會擋下 agent 呼叫「確認裁定」這類指令。
2. **必須在終端機互動確認**：指令只在真人終端機執行時有效，而且要逐條顯示原話與 agent 解讀，並逐條回答同意或不同意。agent 的非互動環境無法執行。
3. **留下紀錄**：記錄確認的時間與 git 使用者名稱。

**誠實的限制**：刻意繞過（例如偽造終端機）的 agent 仍然可能成功。這三層擋的是「順手」或「誤會」造成的越權，不是惡意。

**對使用者的影響**：你需要在終端機跑一個指令（例如 `docspec approve`）。它會一次列出所有待批准的事項，包括待確認的裁定與發布申請，逐條按同意或不同意。

**2026/09/29 裁定**：採用本節的三層防護（乙），並加上分級（丁）：只有會改變決策的裁定需要終端機確認；小裁定只記錄原話，並標示未經本人確認。

## 5. 追溯圖與影響分析

- **節點**：治理層的各種紀錄、文件章節、文件內的決策、文件 change。
- **連結型別**：
  - 回答：裁定 → 問題
  - 依據：決策 → 裁定
  - 取代：新 → 舊
  - 實現：文件章節 → 決策（沿用既有的 realizes，擴充到治理層決策）
  - 指向：工作項目 → 文件或 change
  - 前置：工作項目 → 工作項目
- **建圖方式**：每次執行時從紀錄重新建立，不另存索引。文件領域沿用現有的交叉索引。
- **影響分析**：
  - 裁定被駁回或取代、決策被取代時，沿著連結往下游傳遞，替受影響的項目建立可疑標記。
  - 文件章節不另外建立可疑標記，直接沿用 docspec 既有的「上游變更 → 章節過時」機制，清除時也沿用既有的確認動作（附理由）。這樣不會出現兩套機制。
- **影響檢視**：一個指令同時列出治理層的可疑標記與過時的文件章節。

## 6. 檢視

所有檢視都能輸出成給人讀的 Markdown，也能輸出成給 agent 過濾用的 JSON。

- **目前有效設計**：只列有效的決策，以及它們依據的裁定；可以查詢單條決策的完整歷史。
- **待裁定清單**：待裁定問題與待確認裁定，白話呈現。
- **一頁現況**：
  - 內容：各里程碑的進度、卡住的項目、未處理的可疑標記、待裁定事項、最近的裁定、下一步。
  - 上限兩千字。
  - 每次整份重新產生。
- **追溯查詢**：任一紀錄的上游與下游。

**存放位置**：檢視由指令即時輸出；也可以寫成 `docs/project/` 底下的檔案給人看。寫出的檔案是產生物，防護會擋手改。

- 文件章節的 `realizes` 可以指向治理層決策（例如 `gov:D-0929-k7q`）。
  - 需要擴充決策索引，並讓 11 個使用它的地方一致。
  - 既有章節的指紋不變，不需要重建基準。
- 審查發現加上處置狀態：採納、駁回、延後，並附理由。

**防護修正**

- 只擋寫入與刪除，不擋讀取。
- 凍結區只認 docspec 自己的封存位置，不再把任何名為 archive 的目錄都當成凍結區。
- 原生支援 Codex apply_patch 與 Antigravity 的呼叫格式。

## 8. 指令與 skill

- **指令**（名稱暫定）：
  - `docspec question`：新增、列出、標記待解釋
  - `docspec ruling`：新增（待確認）、列出
  - `docspec approve`：使用者專用，處理所有待批准事項（裁定確認、發布申請）
  - `docspec decision`：新增、取代、列出、查歷史
  - `docspec roadmap`：改為新結構，並提供 `roadmap migrate` 轉換舊檔
  - `docspec impact`
  - `docspec trace`
  - `docspec brief`：一頁現況
- **skill**：新增一個治理用的 skill，給主 agent 使用。內容包括記錄問題與裁定、決策取代、處理可疑標記、產生一頁現況。
- **既有 skill**：develop 改為讀取新的 roadmap。

## 9. 驗收方式

- 驗收測試使用仿照台中港專案結構的合成資料（例如 D7、D13、D15、「刪除就是刪除」、`/tasks` 決策），放進 repo 的測試。
- 使用者的實際專案資料只在本機驗證，不放進 repo。
- **S1**：寫出 D7 的完整新版並取代舊版後，「目前有效設計」只出現新版，歷史可以查到原文與來源。
- **S2（第一期範圍）**：取代「/tasks 維持不變」後，依賴它的文件章節顯示為過時；附理由清除後，過時標示消失。
- **S3**：裁定未確認前，依據它的決策不能轉為有效；非互動環境執行 `approve` 會失敗；agent 透過 hook 呼叫也會被擋下。
- **S4**：一頁現況在兩千字以內，而且符合白話規範。另外做一次展示：請一個沒看過專案的 agent 只讀這一頁，說出現況與下一步。
- **既有的約一千個測試全部保持通過。**

## 12. 實作與驗收紀錄（2026/09/29）

**實作偏離或補充設計之處**

- 決策連結分兩種：`gov:D-…`（決策）在工作項目上是「約束」，只用於追溯與影響分析，不算完成條件；問題與裁定的連結才算完成條件。原因是決策生效不代表工作做完（demo 中發現）。
- 取代者生效時，被取代決策上的可疑標記會自動清除，理由寫「superseded by <新編號>」，避免雜訊。
- 防護判斷相對路徑時，依 hook 輸入的 `cwd` 解析，同時分得出 `docs/g/archive/`（凍結）與 `openspec/changes/archive/`（不凍結）。
- 使用者批准只在有治理層（`docspec/governance/`）的專案強制；舊專案維持原行為，新專案由 `docspec init` 自動啟用。
- 一頁現況依 demo 盲測回饋補上：卡住原因、里程碑到期警告、待批准裁定的解讀、提醒 agent 用 `approve --list`。

**驗收**

- 自動測試：全部 1094 個通過（82 個略過），其中新增約 100 個治理層測試（`tests/test_governance.py`、`test_approve.py`、`test_roadmap_v2.py`、`test_hook_payloads.py`）。
- S1（目前有效設計只出現完整新版，歷史可查）：`test_effective_design_shows_only_the_complete_new_version` 通過。
- S2（第一期範圍：取代決策 → 依賴它的章節轉 stale-upstream，並列入 `impact` 附接替者）：`test_superseding_gov_decision_makes_realizing_section_stale`、`test_impact_lists_doc_sections_on_superseded_decision` 通過。
- S3（未確認的裁定不能讓決策生效；agent 不能執行 approve）：`test_owner_confirms_ruling_then_decision_can_activate`、`test_hook_blocks_agent_calling_approve`、`test_approve_refused_in_agent_environment` 通過。
- S4（一頁現況）：
  - 用仿台中港結構的合成資料建立 demo，一頁現況 1772 字，在兩千字上限內。
  - 兩次請沒看過專案的 agent 只讀這一頁。第二次時它正確說出：各里程碑進度、F-2 明天到期、兩個卡住的項目與原因、待批准事項與待裁定問題；它先用 `approve --list` 與 `docspec impact` 查看，也不代為批准。
  - 它指出的剩餘缺口（上游具體改了什麼、問題的選項）屬於用 `docspec impact`、`question list` 查詢的細節，符合設計。
- 使用者的實際專案資料沒有放進 repo；demo 只在本機產生。
