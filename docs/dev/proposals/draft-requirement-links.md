# F2：文件引用尚未封存的軟體需求

狀態：**負責人已授權，實作與驗收中**。日期：2026/10/03，更新：2026/10/04。來源：[考場實測 F2](../validation/exam-seating-workflow-run.md#9-缺陷與改善建議待後續處理)。前批 `align-delivery-guidance` 只整理方案；後續明確授權由 `add-draft-requirement-links` 實作，不改歷史引用或封條。

## 要解決的問題

軟體的新需求尚在 change 中時，正式規格沒有對應 `req:<capability>/R<n>`。文件目前只能先引用治理依據，軟體封存後才補正式需求。提早封存未完成軟體不能作為解法；已有 `req:` 的解析意義也不能偷偷改成猜活動 change。

## 建議的引用與涵義

新增明確引用 `draft-req:<change-id>/<capability>/R<n>`，例如 `draft-req:add-room-counts/seating/R7`。change ID 在活動與歷史間唯一，能力名稱可有 `/`，需求編號沿用原 R<n>。第一版只支援文件 concept.realizes 的需求層級，不新增 roadmap 成果種類或情境引用。

這個連結表示「引用指定 change 所形成、並在封存後落地的這條需求」。保留原引用與來源身份，並明示來源是草稿還是正式。它不是需求已實作、測試已簽收或軟體已交付的證明。

- **Change 活動中**：沿用現有差異投影與 base fingerprint 檢查，取得該 change 修改後的需求。只接受該 change 確有變動的需求，不借它引用無關正式需求。不同 change 的同一 R 編號不合併。
- **Change 正式封存後**：以該 change 的已封條 baseline 確認落地與編號映射，沿用現有 `renames`，再解析目前正式 `req:`。原 draft-req 字串不自動重寫；輸出同時保留原引用、baseline 與目前正式入口。沒有 renames 表示原編號沿用，仍須確認相應 baseline 與容器身份。
- **正式需求之後再變更**：引用仍跟隨落地的正式需求，沿用現有內容指紋與 stale-software／影響提醒；不自動改文件正文、授權採用新規則或清除影響標記。
- **未落地、刪除、衝突或不可讀**：明示 unresolved／retired／base-conflict／unknown 等原因，不用另一個 change、同編號正式需求或舊來源猜替代者。沒有有效 baseline 不宣稱已落地。

## 完成與歷史界線

未封存軟體的引用只說明來源，不新增文件定版的軟體閘門。缺失／破損軟體來源列軟體診斷，不能表示「已驗證」或「沒有其他限制」；沿用兩域互不阻擋的裁定。原 `req:` 維持正式來源，既有項目不受新語法影響。

文件交付的內容修改、重新審查與新定版仍是明確操作；定版須負責人要求。舊凍結 Markdown、來源指紋、軟體證據與簽收不改寫或重封條。查詢不自動換連結、建立新 store、重算／簽收證據或執行外部 repo。

## 實作方式

若核定，以獨立 OpenSpec change 管理。先建立共用的軟體需求來源解析結果，包含原引用、草稿／正式狀態、實際來源入口、指紋及診斷，讓文件投影、check、追溯、影響與工作摘要共用。

只解析文件實際連結的來源。重用既有容器身份驗證、sealed 讀取、差異投影、baseline renames 及正式需求內容；base 衝突先回診斷，不生成看似有效的需求。以來源種類區分文件依賴與軟體依賴，避免只排除字面 `req:` 而將新前綴誤當文件硬閘。既有來源更新與版本快照讀取須保持唯讀與歷史隔離。

第一版不新增保存檔案或 baseline 欄位。現有資料不足以唯一解析時明示 unknown，不補造映射。文件來源的 seed 自動展開與 CLI 語法僅在另案確認範圍內變更，不因共用目錄而套用軟體 tasks/tests 到文件 change。

## 驗收案例

- 草稿新增及修改需求可引用；無關需求不借 change 投影，兩個 change 的相同 R<n> 不混淆。
- 需求、情境或依據變更提供軟體過時原因；mtime 及無關需求不誤觸。
- 封存前後解析落地來源，涵蓋未重配、需求／情境重配、能力名稱含 `/`、舊容器及搬移。
- 未完成／base 衝突／撤去差異／需求退役／缺 baseline／壞封條／容器身份重複均有明確診斷，不猜來源或假稱已落地。
- 文字與 JSON 相同來源；查詢前後檔案指紋不變，無外部執行，舊 v1/v2 查詢及正式 req: 行為保持。
- 軟體未完成仍可依原文件規則定版；歷史文件、證據、簽收與基線 bytes 不變。
- 兩平台機械回歸後，再以一個全新 agent 的合成兩域案例驗證不必提早封存；該實測獨立手動啟動。

## 需要負責人裁定

是否採用此明確引用，以及「封存後保留原引用、透過已保存映射跟隨正式需求」的涵義。這是來源語法與流程設計的改動，依長期溝通規則須先確認才實作；單純說繼續修正不視為已核定此新語法。
