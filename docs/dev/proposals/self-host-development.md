# 用 ArtiSpec 管理自己的開發

日期：2026/10/04。狀態：負責人提出後續方向，切換方式尚待討論；本輪既有 OpenSpec 工作不切換。

負責人原話：「我剛剛想提案之後可以改由用docspec自己開發自己」。產品目前的執行名稱為 artispec；此原話保留原拼法。

建議從下一輪的小修正試行：共同入口使用 handover、roadmap、roadmap show、change show；需求、裁定、測試簽收、任務、實際證據與封存由既有產品流程管理。文件需要版本化變更時才開文件 change，不把 README 與開發 Markdown 整批搬成 corpus。

目前這輪已開的 OpenSpec changes 先完成並保留為歷史；後續工作使用一套現況來源，不讓 OpenSpec tasks 與 ArtiSpec roadmap 長期雙寫。既有已勾選任務不能直接當作引擎取得的有效證據；初始化必要的現行能力基線應根據已驗證行為，逐項核對匯入結果與測試對應，不宣稱舊紀錄自動通過新條件。

管理流程使用釘版、已驗證的安裝 wheel，開發中的原始碼及候選 wheel 在獨立環境受測；修復管理工具自身缺陷時保存原失敗與紀錄，修復驗證後再明確更新管理版本，不使用未驗證候選版本回填完成。

試行驗收：一個小型軟體修正與必要文件更新，測試作者與實作者分離，完整走需求、簽收、任務、引擎證據及封存，再由全新會話只靠產品入口接手。另保留 Windows／Linux 機械回歸與隔離實測；自用驗證不能取代它們。

需裁定的範圍是正式切換時點、最小現行能力基線與試行工作。這份提案不初始化 repo 的受管資料、不匯入或搬移 OpenSpec，也不宣稱已採用自用開發。
