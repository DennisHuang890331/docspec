# 工程團隊的文件預設風格

日期：2026/10/03，狀態更新：2026/10/04。負責人已明確授權除 README 定稿外依 OpenSpec 實作；具體規則採用，實作與驗收由 engineering-document-defaults 管理，尚未完成。

## 1. 對照結果

已唯讀閱讀負責人指定專案的 README 與部署手冊，以及合成考場案例的排座操作手冊、內建 writing-guide 模板、section-driven schema、concept 指引與 develop／verify skills。參考只抽象出文件的組織、語氣與資訊取捨；不保存真實專案的內容、指令、配置、資產或資料。

參考風格先交代讀者要完成的工作與前置條件，再提供能操作的步驟、預期結果、設定作用及常見錯誤對策。README 給入口，完整操作另查；資訊具體，篇幅按任務需要決定。

排座手冊有操作步驟與限制，但反覆插入「實作者選擇／非負責人指定」與驗收過程，讓使用者需要的操作資訊和案外評估混在一起。這是對文件品質的觀察，不撤銷當時的機械檢查或凍結；原快照、PDF／proof 與歷史保持原貌。

## 2. 目前設計的問題與邊界

- develop 要求每節概念描述論述角色、前節結論成為下節前提，對操作步驟與查詢文件不合適。concept 指引本已容許直接描述本節內容，這兩處應按文件用途一致。
- writing-guide 與 schema 已有 how-to／reference／tutorial／explain，但倒金字塔、所有規則必須結構化及禁止文件導讀等通用措辭過強，容易壓過用途。任務步驟不一定以論述結論開頭，必要的適用範圍、前置條件與導覽也不等於填充文字。
- 禁止內部治理用語是合理邊界；實際操作限制、支援條件及會影響使用者決定的未驗證範圍仍應清楚說明。精簡不能隱藏限制，也不等於把所有驗收狀態寫進每個操作段落。
- 使用 ArtiSpec 的工程團隊與交付文件讀者不同。教師操作手冊仍按教師需要寫；部署、維護、介面與規格文件各按自己的讀者寫，不一律套開發者語氣或章節清單。

另有已重現的流程矛盾：schema 的 develop workflow 仍把 notes.md 說成負責人原話的保存位置；現行 skill 與生成規範要求治理紀錄保存原話、notes 引用。最新已安裝 wheel 的 `artispec guide develop` 仍投影出舊指引，exit 0，查詢前後合成案例檔案未變。這屬既有裁定同步的缺陷，與新風格提案分開判斷。

## 3. 建議的預設

1. **以工作為主**：標題與首段讓讀者知道可完成什麼、何時適用；省去形式化導言與章節報幕。確有用途的範圍、前置條件、快速入口保留。
2. **用途決定組織**：how-to 寫前置條件、順序步驟、預期結果與失敗處理；reference 方便查欄位、介面、設定與限制；explain 交代設計及取捨；tutorial 按學習步驟引導。沿用現有 kind，不要求每份文件都有全部類型。
3. **內容可操作、可核對**：提供有來源的實際命令、輸入／輸出範例、成功判斷與常見錯誤對策。未知資料仍標示缺漏，不從參考專案搬細節，也不為補滿章節造事實或需求。
4. **語氣直接**：用動詞、短段落與必要的條列，保留準確術語。比較或欄位查詢適合表格才用，不把條件與設計取捨全部硬塞成表格。
5. **治理留在來源**：變更理由與依據由既有紀錄追查；操作正文不反覆解釋裁定出自誰或展示測試流水帳。驗證／驗收報告本身仍寫清版本、方法、結果及未覆蓋範圍；使用文件保留真正影響使用的版本與限制說明。

已有專案風格與明確讀者要求直接引用；缺漏才使用工程團隊預設。只有影響設計而缺少的條件才詢問，不新增文類訪談表或必填章節。

## 4. 實作位置與順序

上述具體規則已核定，以獨立 OpenSpec change 管理：

- 調整 `commands/maintenance/init.py` 的 writing-guide 預設，保留專案自行修改內容的既有初始化行為；不把刷新 AGENTS／skills 變成覆寫使用者 writing-guide 的操作。
- 對齊 `schemas/section-driven/schema.yaml` 及 concept 指引，讓投影的通用原則按既有 kind 解釋，與 writing-guide 的專案覆寫關係一致；保留事實來源與規範效力規則。
- develop 不再強制每節成為論述鏈；apply 仍依投影寫作；factcheck 按讀者任務核對完整性、結果及限制，verify 仍核對實際證據。不新增自動語意判斷或跨域完成閘門。
- 同步 guide 的治理來源舊指引，更新內容有變的 skills／生成規範版本；不修改歷史原話、證據、封條或舊版實測文件。
- 不自動重寫 README；中英文 README 的取捨仍由既有待辦另行討論。

## 5. 驗證方式

機械回歸檢查 init 的雙語預設與使用者內容保留、guide／instructions／skills 的同一套來源分工、既有 kind／brief 繼承與覆寫，並在 Windows／實際 Linux runtime 驗證已安裝指令。查詢不寫入，原來源、引用、定版要求與完成判定維持。

行為驗證另用隔離的合成工程案例。新 agent 依新預設產生短操作／部署文件，另一案例產生設計說明或介面參考；每案先指定讀者、來源及必要任務，不給答案。獨立審查核對能否照文件完成任務、成功／失敗判斷是否有據、必要限制是否保留、內部治理與驗收流水帳是否誤入正文。用實際已安裝 CLI 保存命令與產物；風格評估由人審，不把關鍵字命中當作品質通過。

若包含合成文件定版、PDF／proof，案例需明確授權並按既有流程核對同版產物。記錄真正執行的平台、agent 與環境範圍，不以文字規則更新或機械回歸冒稱完整流程實測已通過。
