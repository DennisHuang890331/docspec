# 實測報告：考場座位系統（exam-seating）

- 狀態：**實測已停止**（使用者喊停）。第七、八節是停止後的行為評估與修正。
- 做法：
  - 監管者（我）只轉交訊息、記錄，不替任何角色做決定。
  - 主 agent 用 docspec 工具推進專案。
  - 「負責人」由另一個 agent 扮演（學校教務處組長），不准上網查，只憑記憶回答。
  - 實作者、測試角色、審查者由主 agent 派工，我原文轉交。
- 開場只給一句模糊需求：「我們學校段考排考場座位每次都很麻煩，幫我做個系統。」
- 原始紀錄（不進 repo，在 session 的 scratchpad）：轉交紀錄 85 則、觀察紀錄、注入事件表、獨立評估報告（behavior-review.md）。本檔是整理後的結論。

## 一、結論

1. **docspec 的主要機制在實戰中有效。**
   - 覆述確認：沒有經過負責人確認的決定不會被記錄。
   - 測試簽收：測試簽收後被改動，證據就不成立。
   - 測試異議：實作者認為測試錯了，只能提出異議，不能自己改測試。
   - 證據才能完成任務：前後總共擋下十幾次「測試改了還沒重簽」「測試寫錯」，沒有一次讓錯誤混過去。
   - 實作者在時程壓力下不改測試（注入事件 E4），測試角色拒絕寫放水測試（E5）。
2. **找到 6 個 docspec 本身的缺口，都已修好並推上分支。** 見第三節。
3. **最大的真實問題不在工具，在需求訪談。**
   - 主 agent 做了一個要打指令的系統，做到一半才發現負責人和同事不會用指令。
   - 負責人要的是「Windows 上雙擊就能開、不能安裝任何東西」。
   - docspec 沒有提醒這件事的機制，建議在 AGENTS.md 或提案 skill 加一條：開始設計前，先確認使用者怎麼操作、用什麼電腦、能不能安裝程式。
4. **需求在轉述中遺失，工具看不出來。**
   - 負責人一開始說「隨機打散、同班不相鄰」，後來改成「依學號順序排」。
   - 主 agent 記錄時把「同班不相鄰」也一起丟了，沒有再跟負責人確認。
   - 截圖證實後果：一整間考場 36 個座位都是同一班連號。
   - docspec 忠實保存了原話、覆述、確認三欄，但無法判斷語意有沒有漏。
   - 後來的輪次，主 agent 在負責人加條件時有先覆述再記錄，行為有改善。
5. **子 agent 常在派工尾端自行省略步驟。**
   - 測試角色兩次只做了一部分就回報完成，例如沒跑測試、沒改對應。
   - AGENTS.md 已經寫了「不縮小或跳過任務」，還是擋不住。
   - 主 agent 一次抓到並重派，一次接受了。

## 二、軟體本身（目前狀態）

- **第一版**：5 個功能，21 個測試，全部由引擎證據完成。
- **獨立審查（opus）**：它故意把程式改錯，發現 3 個測試照樣通過；另外找到「轉學生不會出現在列印表上」這類真 bug。
- **之後的修正與新需求**：
  - 保留手動調整；全部重排要確認。
  - 名單有錯整份不匯入。
  - 特殊考場不設上限、達門檻時提醒。
  - 違規調整要確認，並記成例外處理。
  - 每間考場可設定靠門的是哪一排。
  - 查看與取消特殊需求；可以輸入中文需求類型；中文錯誤訊息。
- **第一次全綠**：五個任務由引擎證據完成（51 個測試）。
- **第二次獨立審查（opus）**：仍不能歸檔。3 個會漏人或坐錯的問題（手動調整過的特殊需求學生重排後與一般學生同場、排位後才登記的需求不生效、Excel 範圍標記錯誤時只匯入部分學生）；誤匯入不完整名單會永久刪掉特殊需求；13 個測試故意改錯仍通過；6 個測試掛錯情境；10 處規格與實作矛盾。1,200 人規模排位 0.12 秒、結果正確。
- **目前**：主 agent 已用 docspec 原地修正規格文字；新增 3 條需求（衝突檢查、匯入備份與確認、門牌不露個資）；測試角色在改嚴測試、實作者在修 9 項程式問題。
- **截圖**（實驗專案 `screenshots/`，用 Chromium 實際開啟）：座位表、座號不連續時的門牌、靠後門的考場。
- **操作畫面**：負責人已決定要做，技術評估中，比較三種做法：Windows 執行檔、純網頁檔、在瀏覽器裡跑 Python。

## 三、docspec 本身已修好的缺口

- **登記程式 repo 沒有說明（G1）**：repo 要登記在 config.yaml，但說明、skill、指南都沒寫，agent 只能猜。
  - 修正：新增 `docspec code repo add` 與 `repo list`，會顯示引擎實際要跑的指令（commit 9b5486e）。
- **錯誤訊息誤導（B1）**：repo 沒登記時，簽收的錯誤訊息說「檔案不存在，先寫測試」。
  - 修正：改為說明 repo 沒登記，以及怎麼登記（9b5486e）。
- **測試指令格式（G2）**：不能寫 `PYTHONPATH=src …`；寫 `{tests}` 佔位符也沒有清楚錯誤。
  - 修正：指令開頭可以帶環境變數；寫佔位符會被明確拒絕（9b5486e）。
- **設計清單刪不掉（G3）**：設計文件的目標等清單只能新增，寫錯了改不掉。
  - 修正：`code change design --remove-goal` 等選項（9b5486e）。
- **自己新增的需求改不了字（G4）**：只能撤回再加，連帶弄斷測試連結。
  - 修正：直接修改，編號不變（9b5486e）。
- **測試名稱不一致沒被擋（G5）**：簽收照樣通過；證據只顯示結束碼 4，還誤導成缺 JUnit 設定。
  - 修正：簽收時就擋；證據直接列出找不到的名稱（b9b3472）。

- **引擎狀態顯示舊的失敗原因（G7）**：證據失敗時每個測試印一整句；重簽後狀態仍照舊顯示，測試角色與主 agent 都以為還沒簽。
  - 修正：同一檔的測試合併成一句；已重簽時提示「重跑證據即可」（c9728a6）。
- **簽收以整個測試檔為單位（G6，這次最大的流程摩擦）**：別人在同一檔加測試，其他人的簽收全部失效，重簽來回四輪以上。
  - 修正：新簽收比對「這個測試＋檔案共用部分（import、輔助函式、fixture）」，同檔新增別的測試不影響；舊簽收照舊（6fa4513）。
- **專案裡的 skill 與 AGENTS.md 不會隨 docspec 更新（G8）**：主 agent 三次以為「未歸檔不能改需求文字」、三次「先記錄後覆述」，都是因為它讀的是開場時安裝的舊版。
  - 修正：`docspec brief` 發現專案的 skill 或協作區塊比內建版本舊時，提示重跑 `docspec init --agents-md`（25ee909）。
- **協作規範補強**（d1df071）：寫明專案語言（繁／簡分明）；確認時有增改要再覆述；新決定與既有裁定衝突交給使用者；測試角色不算機械式工作；沒做的步驟要明說。
- **測試角色 skill 補強**（a4fb3c9）：列出兩輪審查找到的寬鬆測試寫法（資料巧合、容量太寬、只測一半流程、永遠成立的檢查、就近掛情境），並要求實跑測試或明說沒跑。

docspec 完整測試：1182 passed。

**監管偏離（照實記錄）**：原本計畫是整輪結束才修 docspec，讓被測版本保持一致。但 G4 和 G5 讓 agent 實際卡住，所以提前修了。修好之後，實驗專案用的就是新版。

## 四、這次實測證明的事

- **證據機制保證的是「規劃的測試有跑、有過、沒被偷改」，不保證「測試抓得到錯」**。引擎全綠後，第二次審查仍找到會漏人的問題與 13 個抓不到改錯的測試。獨立審查（故意改錯）是必要的第二道關。
- **子 agent 說「完成」不可信，引擎才可信**：測試角色回報「全部已簽收」「39 個全過」，引擎顯示並非如此；主 agent 學會先用 `change status` 查證。
- **測試角色的品質跟模型有關**：用 haiku 時多次越界、漏步驟、英文回報、寫出寬鬆測試；sonnet 明顯較好。
- **遺失的需求連審查也看不到**：「同班不相鄰」在第一輪就遺失，規格裡沒有，審查者也就不會查。

## 五、還沒修、留待之後

- **同檔多人協作沒有協調機制**：派工的「誰改哪個檔」只是文字約定；測試角色越界修改別人負責的檔案時，工具擋不住。
- **限制誰能改任務連結**：`code task set` 目前任何角色都能改。
- **身分只靠工具標記**：撰寫、簽收、審查都用同一個標記，主 agent 也代簽過一次。已接受的風險；「角色實例」選填標記尚未決定。
- **測試對應的情境對不對，引擎看不出來**：只能靠審查。

## 六、實測範圍的變化

- 軟體線跑到第二次獨立審查（判定不能歸檔）後，使用者要求縮小範圍、只看文件行為：實作者與測試角色停在修正中途，程式與測試是半成品。
- 文件線：主任版說明寫完初稿（7 節），經事實核對找出寫得太樂觀、門牌隱私承諾與實際相反、12 句沒有第一手來源；主 agent 逐項接受，改寫前使用者喊停。家長版與操作說明沒有開始。
- 沒跑到的注入事件：負責人看截圖發現「同班坐一起」（E9）、學生查詢身分（E8）、換新主 agent 接手（E11）、埋入過時數字（E12）、基線與兩分支合併（E13）。「同班不相鄰」最後是由文件事實核對自然帶出，主 agent 卻把它寫成「負責人決定的結果」。

## 七、停止後的獨立評估（opus，乾淨上下文）

- **大方向符合設計**：先問再做、決定有記錄、測試與實作分開、實作者不改測試改提異議、證據判定完成、兩次獨立審查、沒有擅自定版。
- **最大的問題是追溯鏈沒建起來**：12 條裁定只有 3 條連到決策，需求沒有標依據，文件章節沒有連結，影響分析整場用不上；最早的專案決策與後來的裁定矛盾卻一直有效。原因是規範沒要求、工具沒提醒。
- **監管偏離，照實記錄**：主 agent 三次指定 sonnet 的測試派工被監管者交給一直在跑的 haiku 測試角色；監管者在每份派工前加了「回報用繁體中文」。所以「haiku 品質差」「後段語言都對」兩個結論要打折。
- 評估者把問題分成「流程錯誤」（工具或 skill 設計讓流程出錯）與「agent 表現」（記錯、改寫原話、跳步驟）；使用者要求這次只修前者。

## 八、依評估修正的流程錯誤（使用者裁定見 system-design.md）

- **覆述只在講不清楚時才做**；**新增「資訊」紀錄**（`docspec info`），補回原本「決定／資訊」的另一半（d7b9975）。
- **拿掉 `docspec brief`**，現況看 `docspec roadmap`；**交接單每次整份重寫**（`docspec handover`，6c7032e）。
- **流程卡點**：只存在於 change 的新規格查得到；測試的對應情境可以原地修正；簽收不帶編號只簽有改動的；審查者記錄查核發現不算修改（9af8e90）。
- **連結提醒，都不擋**：新裁定提醒取代舊決策；新需求沒依據時提醒；文件轉述決定、資訊、需求時要連結；定版記下沒連結的章節（bf8125d）。
- 較早已修：文件與軟體互不阻擋（cb85635）、驗證方式寫錯時當場擋下（a4b2e14）。
