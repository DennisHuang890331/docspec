## 2. 問題陳述

依據：台中港資料集專案約三週的實際使用（docspec＋OpenSpec 並用），以及該專案的使用意見檔（2026/09/29）。

現象很多，但可歸結為兩個根本原因：

1. **有權威的資訊沒有正式紀錄，只存在於持續追加的文字檔。** 使用者裁定散在討論檔（單一 change 的 discussion.md 約 260 KB）；設計檔以「D13 取代 D7」「D15 取代 D7 的修訂」層層追加，讀者必須自己合併；總進度檔 234 KB、決定檔 120 KB、交接檔 67 KB，agent 讀不完。模式都是「只追加、後者為準、讀者自行合併」，檔案只增不減。
2. **跨工具的項目之間沒有連結，所以變更不會傳遞。** 裁定、決策、需求、任務、文件章節之間只有人工寫的註記（例如任務標題上的「T2; D1-D3」），工具不檢查。一條決策被取代時，沒有機制列出受影響的規格、任務與文件章節。

docspec 在文件領域已經具備解法的原型：有編號的紀錄、取代鏈、引用關係、上游變更使下游過時、由紀錄產生文件。問題在於這些能力被限制在文件樹內部。

## 3. 利害關係人與關注點

- **專案負責人（使用者）**：做裁定、看進度、驗收。需要白話、一頁看懂；不讀長檔，也不看代號。
- **主 agent**：規劃、設計、審查、派工。需要「目前有效」的規則，以及可信的進度。
- **子 agent（實作或寫作）**：只處理被指派的那一片。需要明確的範圍、寫入權與驗收方式。
- **接手的 agent 或其他工具（Claude、Codex、Gemini）**：需要快速進入狀況，並受同一套防護約束。

---

## 4. 系統層需求

- **SR1 權威單一**：每個事實只有一份權威紀錄，其他都是由它產生的檢視。
- **SR2 可追溯**：裁定 → 決策 → 需求 → 任務 → 交付物（程式、文件），雙向都能追查。
- **SR3 影響分析**：任一紀錄被取代或變更時，系統列出所有受影響的下游項目，不遺漏。
- **SR4 基線與變更控制**：已發布或已封存的內容是基線，只能透過 change 修改。文件 change 與軟體 change 各有自己的生命週期。
- **SR5 狀態可推導**：進度、完成與否、是否過時都由系統從紀錄推導，不靠人或 agent 手寫。
- **SR6 分片讀取**：所有紀錄都可查詢、過濾，agent 只取需要的部分。
- **SR7 判定邊界**：引擎只擋機械上可判定的錯誤；語意上的矛盾交給人與審查，但系統保證「該重看的地方」一個不漏。
- **SR8 工具中立**：各家 agent 共用同一套紀錄、指令與防護。

## 5. 系統架構（三層）

```
┌──────────────────────── 專案治理層（最外層） ────────────────────────┐
│  裁定紀錄            決策紀錄              Roadmap                     │
│  （使用者拍板）      （有效／被取代）      （工作分解與里程碑，進度推導）│
└────────────┬───────────────────────────────────────┬─────────────────┘
             │ 追溯連結                              │ 追溯連結
┌────────────▼──────────────────┐   ┌────────────────▼──────────────────┐
│ 文件領域（既有 docspec）       │   │ 軟體領域（取代 OpenSpec）          │
│ 多文件樹、上下層級約束          │◀─▶│ 能力規格：需求＋情境（扁平，無繼承）│
│ 由紀錄產生文字、過時偵測        │連結│ 軟體 change：提案、規格差異、任務  │
│ 文件 change、發布、匯出         │   │ 驗證證據                            │
└────────────┬──────────────────┘   └────────────────┬──────────────────┘
             └───────────────────┬───────────────────┘
┌────────────────────────────────▼─────────────────────────────────────┐
│ 共用核心                                                              │
│ 紀錄儲存（YAML、編號、結構驗證）｜追溯圖與影響分析｜檢視產生器        │
│ 變更控制與基線｜查詢與過濾｜agent 整合（skill、hook、安裝）          │
└───────────────────────────────────────────────────────────────────────┘
```

### 5.1 專案治理層：決定「要做什麼、以什麼為準」

- **裁定紀錄**：使用者的拍板，是最高權威。只追加，可以取代先前的裁定。
- **決策紀錄**：設計與方向上的決定，帶狀態（有效、被取代、被誰取代），並標明依據哪條裁定。
- **Roadmap**：整個專案只有一份（2026/09/29 裁定）。工作分解與里程碑，項目指向下層的 change 或文件；進度由下層狀態推導，不手寫。
- 不做的事：不存規格內容、不存文件內容。

### 5.2 文件領域：既有 docspec

- 保留多文件樹、上下層級約束、盲寫、過時偵測、發布與匯出。
- 文件章節可以引用治理層的決策，也可以引用軟體領域的需求或 change。
- 段落內部的規範決策仍屬文件內容，留在文件樹裡（2026/09/29 裁定）。

### 5.3 軟體領域：取代 OpenSpec

- **能力規格**：現行的系統行為契約，由需求與情境組成，各自有編號。結構扁平，沒有繼承。
- **軟體 change**：一次修改的單位，包含為什麼改、對哪些需求與情境做差異、任務清單、驗證證據。
- **任務是追溯鏈的最後一段**：每個任務標明實作哪些需求、改了哪些檔案、用哪個測試驗收、證據在哪裡（2026/09/29 裁定）。因此一條裁定或決策被取代時，影響分析可以一路列到具體的檔案與測試。
- 結構依時間組織：change 之間有前後依賴，封存時把差異併回規格，形成新基線。
- 不做的事：不套用文件樹、不做盲寫。

### 5.4 共用核心：兩個領域與治理層共用的機制

- **紀錄儲存**：YAML、固定編號、結構驗證；只能透過指令寫入。
- **追溯圖與影響分析**：所有「引用」形成一張圖；任一節點變更時沿圖列出受影響項目。
- **檢視產生器**：從紀錄產生給人讀的文件，例如目前有效設計、一頁現況、追溯矩陣、總進度。
- **變更控制與基線**：兩個領域的 change 共用同一套概念（開啟、進行、封存成基線），但生命週期與內容各自定義。
- **查詢與過濾**：任何紀錄都能依編號、狀態、欄位取出片段。
- **agent 整合**：skill、hook、安裝；各家工具共用。

## 6. 核心概念（對照系統工程術語）

- **組態項目**：每一筆裁定、決策、需求、任務、文件章節都是可識別、可引用的組態項目。
- **基線**：已發布的文件版本、已封存的軟體 change 所形成的規格現況。
- **變更控制**：任何對基線的修改都透過 change 進行；使用者裁定相當於變更控制委員會的決議。
- **追溯矩陣**：由引用關係自動產生，不手寫。
- **影響分析**：取代或封存發生時自動觸發。

---

## 7. 主要介面

- **治理層 ↔ 兩個領域**：領域內的紀錄以編號引用裁定與決策；roadmap 項目以編號指向領域的 change 或文件。
- **文件領域 ↔ 軟體領域**：文件章節可以宣告依賴某條需求或某個軟體 change；軟體 change 封存後，相關章節標為過時。
- **核心 ↔ agent**：所有讀寫都透過指令；agent 不手改紀錄；給人讀的文件是唯讀輸出。

---

## 8. 運作流程（生命週期）

1. 使用者裁定。
2. 新增或取代決策。
3. 影響分析列出受影響的需求、任務與文件章節。
4. 開啟軟體 change 或文件 change。
5. 實作任務並附上證據。
6. 驗證。
7. 封存，形成新基線。
8. 相關文件自動標為過時。
9. Roadmap 自動推導最新進度。

### 設計原則

- 紀錄是權威，文字是檢視。
- 「目前狀態」可以整份覆寫；「歷史」只能追加。
- 兩個領域各有自己的結構，不互相套用。
- 機械上可判定的錯誤才擋下；語意問題只提示，但保證提示完整。

## 11. 設計審查結論（2026/09/29，三個獨立審查）

審查方式：三個 agent 各自從不同角度檢查本設計——系統工程審查、以台中港專案實際資料驗證、對照 docspec 現有程式的可行性。以下是 Claude 彙整後的結論，**尚未經使用者裁定**。關鍵說法已抽查原始檔案確認。

### 11.1 本設計自己寫錯的地方

- **第 10 節驗收情境一的前提錯了。** D7、D13、D15 不是一條整段取代的鏈：D15 只取代 D7 裡嵌入的 9/24 修訂段落，而且只在「衝突處」取代；D13 同時局部取代 D3、D6.1、D7、D8、D10、D11；D14 只在還原情境推翻原本的非目標。所以「目前有效設計＝D15」不成立，必須靠語意判斷才能合併。
- **情境二的受影響項目也列錯了。** 「第一列任務在第一畫面」屬於已封存的舊規格（task-entry-page），不在 dataset-library 內；D7 對它是「維持不變」的約束關係，設計裡沒有這種連結類型；任務 6.6 早已勾完成，真正的修正是新開的任務 9.6；實際驗收它的是瀏覽器測試（test_entry_page.py），不是單元測試。
- **本紀錄本身就是「只追加的 Markdown」**，正是第 2 節批評的模式。治理層紀錄可用後，應搬進去。

### 11.2 系統層的主要缺陷

1. **取代是局部的，工具無法機械合併。** 建議規則：取代一條決策時，必須寫出合併後的完整新版；舊版與取代來源保留在歷史。這符合「目前狀態整份覆寫、歷史只追加」原則，也才能機械產生「目前有效設計」。
2. **權威來源沒有真實性保證。** 所有裁定都由 agent 轉記；實際資料還有「使用者沒聽懂、待解釋」「暫定」「重新裁定」「部分待定」等狀態；很多裁定其實是使用者對 agent 提案說「可以」；同一條裁定影響多條決策（多對多）。需要：
   - 裁定的生命週期：agent 轉記（待確認）→ 使用者確認後才生效。
   - 權限矩陣：誰可以建立或取代哪類紀錄、誰可以關閉任務、封存 change、發布。
   - 「待使用者裁定的問題」佇列，裁定就是它的答案（討論檔裡約有二十段「待裁定／請確認」）。
3. **「單元測試＝軟體驗收標準」與專案自己的規則衝突。** 專案規定：介面要在 1366×768 與 130% 截圖檢查；機器學習只能用真模型、真影像驗證；有量測門檻（PNG 18 ms 對 JPG 9 ms）；有硬體與容器檢查；有經使用者裁定「暫不驗證」的項目（車輛 bag、NAS、資料碟）。另外，同一個 agent 寫程式又寫測試，等於自己出題自己考。系統工程的做法：
   - 每條需求標「驗證方法」（測試、展示、檢查、分析）。
   - 證據分型別：測試執行、截圖審核、真模型執行、量測對門檻、使用者驗收、豁免（附裁定與重啟條件）。每份證據綁定 commit 與環境；「略過」視為失敗，除非事先聲明。
   - 測試與情境的對應關係，在實作前凍結並審查。
   - 區分「驗證」（做得對不對）與「確認」（使用者接受這是對的東西）。
   - 文件的順序：先跑機械檢查（詞表、引用），再由 LLM 對照寫作規範審查，最後人只看被標出的部分。
4. **影響分析的「一個不漏」只能相對於已記錄的連結。** 忘了建的連結就看不見；連結太粗又會誤報太多。需要：
   - 機械強制建立連結：任務沒有需求編號、測試或存在的檔案，就不能關閉；並產生「孤兒報告」。
   - 連結分類型：實作、驗證、約束（維持不變）、參考，各自有不同的傳遞規則。
   - 影響分析產生「可疑標記」，每個標記要附理由才能清除（比照需求管理工具 DOORS 的 suspect link）。
   - 已完成的任務受影響時，是「標記重看」，不是重新打開。
5. **組態管理不完整。**
   - 缺少跨領域的專案基線：某版文件描述的是哪個規格狀態、哪個 commit，沒有紀錄。
   - 專案是多 repo：工作區沒有 git，程式在 labelvault 自己的 repo。檔案與證據都要帶上 repo 與 commit。
   - 並行分支：單一封條檔在 git 合併時必定衝突，應改成一筆紀錄一個檔。規格差異在封存時合併，要帶「基準指紋」，防止兩個 change 互相覆蓋（OpenSpec 自己的文件就記錄了這個遺失更新的問題）。
   - 凍結區規則會把任何名為 archive 的目錄當凍結區，與 OpenSpec 的封存目錄撞名。
6. **Roadmap「封存＝完成」的推導規則在真實資料上不成立。** dataset-library 封存時有被裁定豁免的未驗證項目；計畫查核點（F-1、F-2，每季）不等於交付物。需要：
   - 「豁免／待驗證」狀態。
   - 把計畫查核點與交付物分開。
7. **缺少的系統需求。**
   - 多 agent 並行：事先宣告的檔案寫入權、測試埠分配。
   - 受保護資源與授權登記：例如使用者的試用任務、唯讀測試任務、正式站埠。
   - 讀取量的量化預算。
   - 引擎故障時的降級：guard 誤擋會卡住所有工作。
   - 遷移。
   - OpenSpec 功能對等清單。
   - 給使用者看的輸出規範：白話、不用代號與表格。
   - 交接紀錄與環境檢查。

### 11.3 可行性（對照現有程式）

- **共用核心大多已存在，只是目前限定在文件樹。**
  - 封條儲存與領域無關，可直接沿用。
  - 「追取代鏈找到目前有效的決策」已有現成函式。
  - 讓文件段落引用專案層決策或軟體需求的成本不高：擴充決策索引並加上命名空間即可，既有指紋不變、不需要重建基準。但要確保 11 個呼叫點一致，否則會誤判過時。
- **最大的衝突是 roadmap 的語意翻轉。** 現在的規則是「在檔＝待辦、做完就移出」，新設計要保留已完成項目並推導進度。這會牽動封存、檢查規則、develop skill，以及 26 個測試檔。
- **軟體 change 可以共用容器的基本部分**（狀態以位置表示、編號規則、搬移、放棄），約 150 行。暫存區、完成判定、封存流程要新寫，因為 git 本身就是暫存區。
- **追溯圖要新建一個模組**，文件領域現有的交叉索引當作它的轉接層。

### 11.4 建議分期（縮小第一版）

- **v1：治理層紀錄＋追溯圖＋影響分析**，用台中港專案驗收。
- **v1.1：軟體領域**，以 OpenSpec 功能對等清單為範圍。
- **v1.2：遷移與多 agent 並行。**

進入細部設計前，先補寫第 11.2 節第 7 點列出的系統需求，並替每條需求寫出可量測的驗收條件。

### 11.5 需要使用者裁定

1. 取代決策時，必須寫出合併後的完整新版，不再允許「以後者為準」式的局部取代？
2. 裁定需經使用者確認才生效（agent 轉記後先是待確認狀態）？
3. 驗證策略修正為：自動化測試是主要與預設的方法，但每條需求標明驗證方法，並接受截圖審核、真模型、量測、使用者驗收、豁免等證據型別？
4. 第一版範圍縮為治理層＋追溯，軟體領域放第二版？
