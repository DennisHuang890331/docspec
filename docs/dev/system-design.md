- 狀態：架構第二版，**已確認（2026/09/29）**；第一期細部設計進行中（分支 `claude/software-domain-redesign`，不併入 main）

- 用途：記錄 docspec 從「文件工具」擴充為「文件＋軟體的專案管理工具」的系統層設計，以及使用者的裁定。本檔只談大方向；細部設計在各期的架構閘通過後另立文件。
- 本檔本身也是「只追加的 Markdown」，正是第 2 節批評的模式。第一期的治理層紀錄可用後，本檔的裁定與決策會搬進去，本檔改由工具產生。

## 2. 問題陳述

依據：台中港資料集專案約三週的實際使用（docspec＋OpenSpec 並用），以及該專案的使用意見檔（2026/09/29）。

兩個根本原因：

1. **有權威的資訊沒有正式紀錄，只存在於持續追加的文字檔。** 使用者裁定散在討論檔（單一 change 的 discussion.md 約 260 KB）；設計檔以「D13 取代 D7」「D15 取代 D7 的修訂」層層追加，而且取代只發生在「衝突處」，讀者必須自己合併；總進度檔 234 KB、決定檔 120 KB、交接檔 67 KB，agent 讀不完。
2. **跨工具的項目之間沒有連結，所以變更不會傳遞。** 裁定、決策、需求、任務、文件章節之間只有人工註記（例如任務標題上的「T2; D1-D3」），工具不檢查。一條決策被取代時，沒有機制列出受影響的規格、任務、測試與文件章節。

docspec 在文件領域已經具備解法的原型：有編號的紀錄、取代鏈、引用關係、上游變更使下游過時、由紀錄產生文件。問題在於這些能力被限制在文件樹內部。

## 3. 利害關係人與關注點

- **專案負責人（使用者）**：做裁定、看進度、驗收。需要白話、一頁看懂；不讀長檔，也不看代號。
- **主 agent**：規劃、設計、審查、派工。需要「目前有效」的規則、待裁定的問題清單，以及可信的進度。
- **子 agent（實作或寫作）**：只處理被指派的那一片。需要明確的範圍、寫入權與驗收方式。
- **接手的 agent 或其他工具（Claude、Codex、Gemini）**：需要快速進入狀況，並受同一套防護約束。

## 4. 系統需求（第二版）

每條需求附驗收條件、驗證方法與所屬期別。驗證方法用系統工程的四類：測試、展示、檢查、分析。

**權威與紀錄**

- **SR1 權威單一**：每一類紀錄只有一個存放位置；給人讀的檔案都是工具產生的檢視，不接受手改。
  - 驗收：每類紀錄的位置有定義；手改產生的檢視會被偵測並拒絕。
  - 方法：測試。第一期。
- **SR2 裁定真實性**：agent 轉記的裁定先為「待確認」，只有使用者本人的動作能使它生效。裁定保存使用者原話、轉記者、agent 的解讀，以及它回答了哪個待裁定問題。
  - 驗收：未確認的裁定不能作為任何決策的依據。
  - 方法：測試。第一期。
- **SR3 待裁定問題**：需要使用者決定的事，列成一份有狀態的清單（待解釋、待裁定、暫定、已裁定）。
  - 驗收：使用者一次就能看到全部待決事項。
  - 方法：展示。第一期。
- **SR4 完整取代**：取代一條決策時必須寫出合併後的完整新版。「目前有效設計」由工具機械產生，只含有效版本；歷史保留全部舊版與取代來源。
  - 驗收：驗收情境 S1。
  - 方法：測試。第一期。
- **SR5 權限**：一張權限表規定誰可以建立、取代、確認各類紀錄，以及誰可以關閉任務、封存 change、發布文件。
  - 驗收：越權的動作被拒絕，並說明原因。
  - 方法：測試。第一期（基本版）。

**追溯與影響**

- **SR6 有型別的追溯**：紀錄之間的連結分類型（依據、實作、驗證、約束、參考），雙向可查。
  - 驗收：任一紀錄都能列出它的上游與下游。
  - 方法：測試。第一期。
- **SR7 影響分析**：任一紀錄被取代或變更時，沿著已記錄的連結列出所有受影響的項目，並標成「可疑」。每個可疑標記要附理由才能清除；已完成的項目標記重看，不重新打開。
  - 驗收：驗收情境 S2。
  - 方法：展示。第一期（治理層＋文件），第二期（延伸到軟體）。
- **SR8 連結完整性**：該建的連結由工具強制建立。例如任務沒有對應的需求、檔案與證據就不能關閉；並定期產出「孤兒報告」，列出沒有下游的決策或需求。
  - 驗收：缺連結的關閉動作被拒絕。
  - 方法：測試。第一期（決策與文件），第二期（任務）。

**基線與變更**

- **SR9 變更控制**：已發布或已封存的內容是基線，只能透過 change 修改。文件 change 與軟體 change 分開，各有自己的生命週期。
  - 驗收：繞過 change 直接改基線會被偵測。
  - 方法：測試。第一期（文件，沿用既有機制），第二期（軟體）。
- **SR10 專案基線**：一個專案版本同時釘住治理層、文件、軟體規格的狀態，以及對應的程式 commit（支援多個 repo）。
  - 驗收：能回答「文件第三版描述的是哪個規格、哪個 commit」。
  - 方法：展示。第二期。
- **SR11 並行安全**：多個分支或多個 agent 同時新增紀錄，合併時不產生衝突，也不需要手動重新封條。規格差異封存時帶基準指紋，防止兩個 change 互相覆蓋。
  - 驗收：驗收情境 S6。
  - 方法：測試。儲存格式在第一期就決定（一筆紀錄一個檔）；多 agent 的寫入權宣告在第三期。

**驗證與狀態**

- **SR12 驗證方法與證據**：每條需求標明驗證方法。證據有型別：測試執行、截圖審核、真模型執行、量測對門檻、使用者驗收、豁免（附裁定與重啟條件）。每份證據綁定 commit 與環境；「略過」視為失敗，除非事先聲明。測試與需求的對應在實作前確定。
  - 驗收：驗收情境 S5。
  - 方法：測試。第二期。
- **SR13 驗證與確認分開**：「做得對不對」（驗證）與「使用者接受這是對的東西」（確認）是兩個獨立的狀態。
  - 驗收：可以有「已驗證、未確認」的項目。
  - 方法：檢查。第二期。
- **SR14 文件驗證**：文件依序跑機械檢查（詞表、引用、格式）、LLM 對照寫作規範審查、人只看被標出的部分。LLM 的每個發現都要被處置（採納、駁回、延後）。
  - 驗收：人不需要讀全文就能完成審核。
  - 方法：展示。第一期（沿用 factcheck，補處置狀態）。
- **SR15 狀態推導**：進度、完成與否、是否過時都由系統推導。狀態包含「完成（含豁免）」；計畫查核點與交付物分開。
  - 驗收：驗收情境 S4、S5。
  - 方法：測試。第一期（治理層與文件），第二期（軟體）。

**使用與整合**

- **SR16 分片讀取與讀取預算**：任何紀錄都能依編號、狀態、欄位查詢。「一頁現況」有長度上限（暫定兩千字以內）。
  - 驗收：接手的 agent 只讀一頁現況，就能說出目前狀態與下一步。
  - 方法：展示。第一期。
- **SR17 使用者可讀的輸出**：給使用者看的內容一律白話、條列，編號只放在括號裡。
  - 驗收：一頁現況與待裁定清單符合這個規範。
  - 方法：檢查。第一期。
- **SR18 工具中立與降級**：Claude、Codex、Gemini、Antigravity 共用同一套紀錄、指令與防護。防護只擋寫入，不擋讀取；防護本身出錯時，不能卡住所有工作。
  - 驗收：四家的 hook 都能擋下對基線的寫入，而且讀取不被誤擋。
  - 方法：測試。第一期。
- **SR19 OpenSpec 功能對等**：列出 OpenSpec 的功能清單，逐項提供對應功能。清單在第二期開始前定稿。
  - 方法：檢查。第二期。
- **SR20 遷移**：既有 docspec 專案（含舊的每份文件各自一份 roadmap）與 OpenSpec 專案都能匯入。
  - 方法：展示。OpenSpec 匯入在第二期，既有 docspec 專案遷移在第三期。
- **SR21 接手支援**：一頁現況每次整份重新產生；交接歷史只追加；有環境檢查指令，在接手時執行。
  - 方法：展示。第一期（一頁現況），第三期（環境檢查）。

## 5. 系統架構（第二版）

```
┌──────────────────────────── 專案治理層（最外層）────────────────────────────┐
│  待裁定問題 ──答案──▶ 裁定（待確認→生效） ──依據──▶ 決策（完整新版＋歷史）  │
│  Roadmap（唯一一份：里程碑 → 工作項目 → change／文件；進度推導）           │
│  權限表                                                                     │
└───────────────┬────────────────────────────────────────────┬────────────────┘
                │ 有型別的追溯連結                            │
┌───────────────▼─────────────────┐          ┌───────────────▼─────────────────┐
│ 文件領域（既有 docspec）          │  依賴／  │ 軟體領域（取代 OpenSpec，第二期）│
│ 多文件樹、上下層級約束            │◀─描述──▶│ 能力規格：需求＋情境（扁平）     │
│ 由紀錄產生文字、過時偵測          │          │ 軟體 change：差異、任務、依賴    │
│ 文件 change、發布、匯出           │          │ 任務 → 檔案／測試（repo＋commit）│
│ 發現（LLM 審查）與處置            │          │                                  │
└───────────────┬─────────────────┘          └───────────────┬─────────────────┘
                └──────────────────────┬──────────────────────┘
┌──────────────────────────────────────▼──────────────────────────────────────┐
│ 共用核心                                                                     │
│ 紀錄儲存（一筆一檔、編號含命名空間）｜追溯圖、影響分析、可疑標記             │
│ 證據紀錄（有型別、綁 commit 與環境）｜變更控制與專案基線                     │
│ 檢視產生器（目前有效設計、一頁現況、待裁定清單、追溯矩陣）｜查詢與過濾       │
│ agent 整合（skill、hook、安裝；只擋寫入）                                   │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 5.1 專案治理層：決定「要做什麼、以什麼為準」

- **待裁定問題**：agent 提出、需要使用者決定的事，有狀態。
- **裁定**：使用者的拍板，是最高權威。先是待確認，使用者確認後生效；可以回答一或多個待裁定問題，影響一或多條決策。
- **決策**：跨領域的方向性決定。取代時必須寫出完整新版，並標明依據哪些裁定。
- **Roadmap**：整個專案唯一一份。里程碑 → 工作項目 → 指向 change 或文件；計畫查核點與交付物分開；進度由下層推導。
- **權限表**：誰可以做什麼。
- 不做的事：不存規格內容、不存文件內容。

### 5.2 文件領域：既有 docspec

- 保留多文件樹、上下層級約束、盲寫、過時偵測、發布與匯出。
- 文件章節可以依賴治理層的決策，也可以依賴軟體領域的需求或 change；上游被取代或封存時，章節標為過時。
- 段落內的規範決策仍屬文件內容，留在文件樹。
- 審查發現（factcheck）留在文件領域，並補上處置狀態。

### 5.3 軟體領域：取代 OpenSpec（第二期）

- **能力規格**：現行的系統行為契約，需求與情境各有編號。結構扁平，沒有繼承；每條需求標明驗證方法。
- **軟體 change**：為什麼改、對哪些需求與情境做差異（可以只改某個情境）、任務、前後依賴。git 本身就是暫存區。
- **任務**：實作哪些需求、改了哪些檔案、用哪個測試驗收、證據在哪裡；檔案帶上 repo 與 commit。
- 不做的事：不套用文件樹、不做盲寫。

### 5.4 共用核心

- **紀錄儲存**：YAML，一筆紀錄一個檔（為了多分支合併），編號帶命名空間以避免撞號；只能透過指令寫入。
- **追溯圖**：所有連結組成一張圖，每次執行時重新建立，不另存索引；文件領域現有的交叉索引作為它的一部分。
- **影響分析與可疑標記**：取代或封存時沿圖標記可疑項目，每個標記要附理由才能清除。
- **證據紀錄**：兩個領域共用的證據型別。
- **變更控制與專案基線**：兩個領域的 change 共用容器的基本機制（狀態、編號、搬移、放棄）；專案基線釘住三層狀態與 commit。
- **檢視產生器**：目前有效設計、一頁現況、待裁定清單、追溯矩陣、總進度。
- **查詢與過濾**、**agent 整合**。

## 6. 核心概念（對照系統工程術語）

- **組態項目**：每一筆待裁定問題、裁定、決策、需求、任務、證據、文件章節，都可識別、可引用。
- **變更控制委員會**：使用者本人。裁定就是委員會的決議，必須經本人確認。
- **基線**：已發布的文件版本；已封存的軟體 change 形成的規格現況；以及把兩者與 commit 釘在一起的專案基線。
- **追溯矩陣**：由有型別的連結自動產生。
- **可疑連結**：上游變了，下游必須有人看過並附理由，才能解除。
- **驗證與確認**：驗證問「做得對不對」，確認問「是不是使用者要的」。

---

## 7. 外部與內部介面

- **使用者**：確認裁定、回答待裁定問題、驗收；讀一頁現況與待裁定清單。
- **git**：可能有多個 repo，工作區本身也可能沒有 git。任務的檔案與證據要帶上 repo 與 commit。
- **測試執行**：跑測試並把結果寫成證據紀錄，包含指令、commit、環境、通過／略過／失敗數。
- **LLM 審查**：輸入是文件與寫作規範；輸出是待處置的發現。
- **agent**：所有讀寫都透過指令；防護只擋寫入。
- **治理層 ↔ 兩個領域**：以編號互相引用。
- **文件領域 ↔ 軟體領域**：雙向。文件可以描述軟體；某些文件（例如資料格式規範）也可能是軟體需求的依據。

## 8. 運作流程（生命週期）

1. agent 發現需要使用者決定的事，建立待裁定問題。
2. 使用者回答，agent 轉記成裁定（待確認）→ 使用者確認後生效。
3. 依裁定新增決策，或寫出完整新版取代舊決策。
4. 影響分析把受影響的需求、任務、測試、文件章節標為可疑。
5. 開啟軟體 change 或文件 change 來處理。
6. 實作並產生有型別的證據（驗證）。
7. 使用者驗收（確認）。
8. 封存，形成新基線；相關文件標為過時。
9. Roadmap 與一頁現況自動更新。

設計原則：

- 紀錄是權威，文字是檢視。
- 「目前狀態」整份覆寫；「歷史」只追加。
- 兩個領域各有自己的結構，不互相套用。
- 機械上可判定的錯誤才擋下；語意問題只標可疑，但每個標記都要處理。
- 使用者是唯一的最終權威，而且這件事要由工具保證，不是靠 agent 自律。

## 10. 驗收情境（以台中港專案為測試資料）

- **S1 目前有效設計（第一期）**：以 D13、D15 為來源寫出 D7 的完整新版後，「目前有效設計」只出現新版。歷史可以查到 D7 原文、D13、D15，以及它們依據的裁定。
- **S2 影響分析**：取代「/tasks 頁面維持不變」這條決策時，系統把下列項目全部標為可疑：
  - 已封存舊規格裡的需求「第一列任務在第一畫面」；
  - 已完成的任務 6.6（標記重看，不重開）；
  - 驗收它的瀏覽器測試（test_entry_page.py）；
  - 說明書的相關章節。

  每個標記附理由清除後才會消失。第一期只驗證決策 → 文件章節這一段；第二期驗證完整鏈。
- **S3 裁定真實性（第一期）**：agent 轉記裁定「刪除就是刪除」後，在使用者確認之前，依據它修改的決策不能成為有效版本；使用者確認後才生效。
- **S4 一頁現況（第一期）**：用台中港資料產生的一頁現況在兩千字以內，包含各工作項目的狀態、卡住的項目、待裁定問題與最近的裁定，而且符合白話規範。一個沒看過專案的 agent 只讀這一頁，就能正確說出目前狀態與下一步。
- **S5 豁免（第二期）**：dataset-library 封存時未驗證的項目（車輛 bag、NAS、資料碟）以豁免證據呈現；roadmap 顯示「完成（含豁免三項）」，不是單純的「完成」。
- **S6 並行（第三期）**：兩個 agent 在不同分支各自新增決策與裁定，合併時沒有衝突，也不需要手動重新封條。
