### 文件版本目錄核定（2026/10/01）

使用者確認版本目錄提案後，原話「可以你開始實作了嗎?」。核定 `docspec/changes/_versions/<article>/<version>/snapshot/document.md` 與 `snapshot/assets/` 保存不可變的定版 Markdown、當版實際引用的受管圖資產；snapshot 整夾受 hash 與 hook 防護。文章根存 `history.md`；各版 exports／proof 是可再生輸出，不在 snapshot 中。未定版 preview 的輸出放文章根 `_preview/exports/`、`_preview/proof/`。docs 留工作 latest、工作資產與既有 latest 匯出輸出；指定版與最新定版的輸出收在版本區。

此條明確取代文件定版寫入 `docs/archive/`、歷史寫入 `docs/revision_history/` 的儲存規則。普通文件／軟體 change 與 `_archive/` 的格式、建立時機及完成判定不變；初次 freeze 不須為了儲存版本而先建新 change。現有 sealed document／project baseline 的位置、內容、封條不動，不重封條或用當前內容洗白歷史。

新定版只寫新位置；讀取保留舊路徑 fallback 與舊保護。同文章同版的新舊快照並存必須報錯，內容相同也不能挑一份。新增 `artispec versions [article] [--json]` 唯讀列出來源，`artispec versions migrate [article] --dry-run`／實跑明確搬移，省略 article 處理全部。搬移全批次先驗證舊 `.freeze.yaml`、原快照 hash、目標／history 碰撞與解析後路徑；只把已驗證的原 manifest hash 換 key，原 snapshot bytes 不改，失敗回復，不在查詢時自動搬移。freeze 遇未搬的舊 history 先拒絕並提示 migrate，避免兩份歷史。

freeze 保存所引用的受管圖資產；新 snapshot 缺圖不得 fallback 到 current。舊 Markdown 缺當版圖片來源時如實列 unknown provenance／缺圖，不複製目前資產造歷史。匯出舊版或 preview 不得清掉其他版或 latest，proof 須使用所選版的實際匯出。此案由 `relocate-document-versions` 管理，實作與獨立驗證結果見 [版本儲存驗證](validation/document-version-storage-run.md)；不回填先前六案驗收。history 的不安全寫入路徑在建立新版前拒絕，snapshot 登記與 migration 的回復不等同整條 freeze 的跨檔案交易。

舊 Markdown 本身有效時可完成搬移，即使歷史圖來源未知也必須保留警告；export 無版本圖資產就明確拒絕。舊無版號 proof 只收文章根 `_legacy-proof/` 並標 unknown，不能猜成某版。既有 register-legacy 的任意歷史檔改收 `_versions/_legacy/<name>/snapshot/`，保留原格式／bytes／verified hash、不假成 semver 或納入文章版本序列；舊 `docs/archive/legacy/` 仍讀，default all explicit migrate 包含此 collection。這只調整舊 API 儲存位置，不新增治理 record type；保留名稱撞到既有文章或版本時先報錯。

## 2. 問題陳述

依據：台中港資料集專案約三週的實際使用（docspec＋OpenSpec 並用），以及該專案的使用意見檔（2026/09/29）。

兩個根本原因：

1. **有權威的資訊沒有正式紀錄，只存在於持續追加的文字檔。** 使用者裁定散在討論檔（單一 change 的 discussion.md 約 260 KB）；設計檔以「D13 取代 D7」「D15 取代 D7 的修訂」層層追加，而且取代只發生在「衝突處」，讀者必須自己合併；總進度檔 234 KB、決定檔 120 KB、交接檔 67 KB，agent 讀不完。
2. **跨工具的項目之間沒有連結，所以變更不會傳遞。** 裁定、決策、需求、任務、文件章節之間只有人工註記（例如任務標題上的「T2; D1-D3」），工具不檢查。一條決策被取代時，沒有機制列出受影響的規格、任務、測試與文件章節。

docspec 在文件領域已經具備解法的原型：有編號的紀錄、取代鏈、引用關係、上游變更使下游過時、由紀錄產生文件。問題在於這些能力被限制在文件樹內部。

## 4. 系統需求（第二版）

每條需求附驗收條件、驗證方法與所屬期別。驗證方法用系統工程的四類：測試、展示、檢查、分析。

**權威與紀錄**

- **SR1 權威單一**：每一類紀錄只有一個存放位置；給人讀的檔案都是工具產生的檢視，不接受手改。
  - 驗收：每類紀錄的位置有定義；手改產生的檢視會被偵測並拒絕。
  - 方法：測試。第一期。
- **SR2 裁定可信度**（2026/09/30 現行裁定）：裁定保存使用者原話、轉記者與它回答的待裁定問題，寫入即生效。使用者講得清楚就直接記；只有不清楚時，agent 才先覆述並等確認，另存覆述與回覆。使用者提供的事實用資訊紀錄，不能當成裁定。事後駁回會觸發影響分析。
  - 驗收：明確裁定可不填覆述與確認回覆；不清楚的內容先釐清再記；被駁回的裁定不能作為有效決策依據。工具保存來源，但不保證轉記文字確實出自本人。
  - 方法：測試。第一期。
- **SR3 待裁定問題**：需要使用者決定的事，列成一份有狀態的清單（待解釋、待裁定、暫定、已裁定）。
  - 驗收：使用者一次就能看到全部待決事項。
  - 方法：展示。第一期。
- **SR4 完整取代**：取代一條決策時必須寫出合併後的完整新版。「目前有效設計」由工具機械產生，只含有效版本；歷史保留全部舊版與取代來源。
  - 驗收：驗收情境 S1。
  - 方法：測試。第一期。
- ~~SR5 權限~~：2026/09/30 取消（單人使用，不做多人權限）。

**追溯與影響**

- **SR6 有型別的追溯**：紀錄之間的連結分類型（依據、實作、驗證、約束、參考），雙向可查。
  - 驗收：任一紀錄都能列出它的上游與下游。
  - 方法：測試。第一期。
- **SR7 影響分析**：任一紀錄被取代或變更時，沿著已記錄的連結列出所有受影響的項目，並標成「可疑」。每個可疑標記要附理由才能清除；已完成的項目標記重看，不重新打開。
  - 驗收：驗收情境 S2。
  - 方法：展示。第一期（治理層＋文件），第二期（延伸到軟體）。
- **SR8 追溯提醒與完成必要條件**：需求缺 `based-on`、章節缺 `realizes`、roadmap 工作缺連結是追溯提醒，不阻擋定版或封存。軟體必要情境、規劃測試、實作任務與有效證據之間的關係則是完成條件；缺少必要關係或有效證據，不得宣稱完成或封存。
  - 尚未封存的變動需求用 `draft-req:<change>/<capability>/R<n>` 明確引用；封存後保留原引用，由唯一 sealed baseline／renames 指向正式來源。來源缺失或失效明示，不猜其他同編號需求、不自動改連結；來源診斷是軟體問題，不新增文件硬依賴。
  - `check` 的 coverage 只解釋已做機械檢查及未做語意／交付審查，保留原退出碼；過時預覽仍可能掃過引用，正式正文同步未評估明示。工程文件預設按任務與交付讀者、kind／writing-guide 組織，不固定論述鏈或必填章節。
  - 驗收：缺追溯連結只提醒；缺必要測試與證據不能完成或封存。結構錯誤及不存在的引用仍須修正；文件與軟體各自驗收，差異只記錄。
  - 方法：測試。第一期（治理與文件），第二期（任務及證據）。

**基線與變更**

- **SR9 變更控制**：已發布或已封存的內容是基線，只能透過 change 修改。文件 change 與軟體 change 分開，各有自己的生命週期。
  - 驗收：繞過 change 直接改基線會被偵測。
  - 方法：測試。第一期（文件，沿用既有機制），第二期（軟體）。
- **SR10 專案基線**：一個專案版本同時釘住治理層、文件、軟體規格的狀態，以及對應的程式 commit（支援多個 repo）。
  - 驗收：能回答「文件第三版描述的是哪個規格、哪個 commit」。
  - 方法：展示。第二期。
- **SR11 基準防覆蓋**：規格差異帶 base fingerprint，封存時檢查基準未變，避免舊 change 覆蓋新版內容。產品不支援多 agent 並行寫入受管理紀錄或多人編輯，不保證跨分支合併無衝突。
  - 驗收：兩個 change 依同一基準修改相同內容，第一個封存後，第二個因基準不符被拒絕。
  - 方法：測試。第二期。原 S6 已取消；docspec 原始碼開發仍可依難度分派 agent，指定檔案負責人。

**驗證與狀態**

- **SR12 驗證方法與證據**：每條需求標明驗證方法。證據有型別：測試執行、截圖審核、真模型執行、量測對門檻、使用者驗收、豁免（附裁定與重啟條件）。每份證據綁定 commit 與環境；「略過」視為失敗，除非事先聲明。測試與需求的對應在實作前確定。
  - 驗收：驗收情境 S5。
  - 方法：測試。第二期。
- **SR13 驗證與確認分開**：「做得對不對」（驗證）與「使用者接受這是對的東西」（確認）是兩個獨立的狀態。
  - 驗收：可以有「已驗證、未確認」的項目。
  - 方法：檢查。第二期。
- **SR14 文件驗證**：文件依序跑機械檢查（詞表、引用、格式）、LLM 對照寫作規範審查、人只看被標出的部分。LLM 的每個發現都要被處置（採納、駁回、延後）。
  - 驗收：人不需要讀全文就能完成審核。
  - 方法：展示。第一期（沿用 factcheck，補處置狀態）。
- **SR15 狀態推導**：進度、完成與否、是否過時都由系統推導。狀態包含「完成（含豁免）」；計畫查核點與交付物分開。
  - 驗收：驗收情境 S4、S5。
  - 方法：測試。第一期（治理層與文件），第二期（軟體）。

**使用與整合**

產品支援 Windows 與 Linux。命令列、檔案路徑與測試執行器須在兩平台驗證；平台專用的實驗啟動器不得被當成產品唯一入口。機械回歸與 E11 接手實測分開報告各自實際執行的平台。

- **SR16 分片讀取與讀取預算**：任何紀錄都能依編號、狀態、欄位查詢。「一頁現況」有長度上限（暫定兩千字以內）。
  - 驗收：接手的 agent 只讀一頁現況，就能說出目前狀態與下一步。
  - 方法：展示。第一期。
  - 現行核定範圍：`roadmap` 找到工作後，以唯讀 `roadmap show <W> [--json]` 集中該工作明確關聯的來源、現況與問題，必要時回到原始紀錄。正常項目以數量概述，問題的識別碼與原因及有效決策內容保留。這不代表任意欄位查詢、硬性兩千字上限或只讀一頁掌握全專案已實現；不得截斷必要原因來假稱符合讀取預算。摘要不另存紀錄，也不縮小完整驗證範圍。
- **SR17 使用者可讀的輸出**：給使用者看的內容一律白話、條列，編號只放在括號裡。
  - 驗收：一頁現況與待裁定清單符合這個規範。
  - 方法：檢查。第一期。
- **SR18 工具中立與降級**：Claude、Codex、Gemini、Antigravity 共用同一套紀錄、指令與防護。防護只擋寫入，不擋讀取；防護本身出錯時，不能卡住所有工作。
  - 驗收：四家的 hook 都能擋下對基線的寫入，而且讀取不被誤擋。
  - 方法：測試。第一期。
- **SR19 OpenSpec 功能對等**：列出 OpenSpec 的功能清單，逐項提供對應功能。清單在第二期開始前定稿。
  - 方法：檢查。第二期。
- **SR20 遷移**：既有 docspec 專案（含舊的每份文件各自一份 roadmap）與 OpenSpec 專案都能匯入。
  - 方法：展示。OpenSpec 匯入在第二期，既有 docspec 專案遷移在第三期。
- **SR21 接手支援**：現況由 `roadmap` 即時推導；找到工作後以 `roadmap show <W>` 查其唯讀摘要，再按需要看原始紀錄。`handover` 是每次整份重寫的交接單，不追加歷史。讀取時提示交接單的新鮮度及內建協作規範／skills 更新；接手依需要執行環境檢查。開工沿用同範圍工作項，缺少才登記並連到實際工作。摘要缺資料須明示，不視為無限制；被取代的引用不自動授權套用新版，角色及定版授權不因摘要的動作建議而改變。
  - 方法：展示。第一期（一頁現況），第三期（環境檢查）。
- **SR22 文件版本保存與搬移**：依 2026/10/01 明確核定，版本 snapshot 的 Markdown 與當版受管 assets 不可變，exports/proof 可再生，history 收文章根。唯讀 versions 提供原始來源；同版雙副本拒絕，明確 migration 只 rekey verified 原 hash，不改 sealed baseline。缺歷史圖來源不能由 current 補造，舊保護與 read fallback 保留。
  - 驗收：初次 freeze、當版資產不變、舊讀取／同版衝突、乾跑／全批次預檢與回復、manifest／baseline 保存、按版輸出隔離。
  - 方法：獨立行為測試、實際 PDF/proof 與 review。Windows 最終完整回歸 1729 passed、1 skipped，Linux 實際 WSL runtime 1726 passed、4 skipped；兩平台 PDF/proof/座標各 86 passed，詳見版本儲存驗證報告。

### 5.1 專案治理層：決定「要做什麼、以什麼為準」

- **待裁定問題**：agent 提出、需要使用者決定的事，有狀態。
- **裁定**：使用者的拍板，是最高權威。清楚就保存原話、寫入即生效，不清楚才先覆述等確認；可以回答一或多個待裁定問題，影響一或多條決策。
- **資訊**：使用者提供的事實，保存原話與來源，可被文件引用與查核；不代替決定。
- **決策**：跨領域的方向性決定。取代時必須寫出完整新版，並標明依據哪些裁定。
- **Roadmap**：整個專案唯一一份。里程碑 → 工作項目 → 指向 change 或文件；計畫查核點與交付物分開；進度由下層推導。
- **交接單**：保存工作進展、承諾、注意事項與下一步，每次整份重寫；現況仍以 roadmap 和被引用紀錄為準。
- 不做的事：不存規格內容、不存文件內容。

### 5.2 文件領域：既有 docspec

- 保留多文件樹、上下層級約束、盲寫、過時偵測、定版與匯出。
- 文件章節可以依賴治理層的決策與資訊，也可以依賴軟體領域的需求或 change；依其引用關係偵測過時。僅軟體差異造成的 `stale-software` 不阻擋文件定版，定版紀錄保存差異；軟體封存不依賴文件完成。
- 段落內的規範決策仍屬文件內容，留在文件樹。
- 審查發現（factcheck）留在文件領域，並補上處置狀態。

### 5.3 軟體領域：取代 OpenSpec（第二期）

- **能力規格**：現行的系統行為契約，需求與情境各有編號。結構扁平，沒有繼承；每條需求標明驗證方法。
- **軟體 change**：為什麼改、對哪些需求與情境做差異（可以只改某個情境）、任務、前後依賴。git 本身就是暫存區。
- **任務**：實作哪些需求、改了哪些檔案、用哪個測試驗收、證據在哪裡；檔案帶上 repo 與 commit。
- 不做的事：不套用文件樹、不做盲寫。

### 5.4 共用核心

- **紀錄儲存**：YAML，一筆紀錄一個檔，編號包含工具前綴，便於識別与查詢；只能透過指令寫入。此格式不保證並行寫入或跨分支合併安全。
- **追溯圖**：所有連結組成一張圖，每次執行時重新建立，不另存索引；文件領域現有的交叉索引作為它的一部分。
- **影響分析與可疑標記**：取代或封存時沿圖標記可疑項目，每個標記要附理由才能清除。
- **證據紀錄**：兩個領域共用的證據型別。
- **變更控制與專案基線**：兩個領域的 change 共用容器的基本機制（狀態、編號、搬移、放棄）；專案基線釘住三層狀態與 commit。
- **檢視產生器**：目前有效設計、一頁現況、待裁定清單、追溯矩陣、總進度。
- **查詢與過濾**、**agent 整合**。

## 6. 核心概念（對照系統工程術語）

- **組態項目**：每一筆待裁定問題、裁定、決策、需求、任務、證據、文件章節，都可識別、可引用。
- **變更控制委員會**：使用者本人。裁定就是使用者明確做出的決定；agent 保存原話，只有內容不清楚才請其確認理解。
- **基線**：已發布的文件版本；已封存的軟體 change 形成的規格現況；以及把兩者與 commit 釘在一起的專案基線。
- **追溯矩陣**：由有型別的連結自動產生。
- **可疑連結**：上游變了，下游必須有人看過並附理由，才能解除。
- **驗證與確認**：驗證問「做得對不對」，確認問「是不是使用者要的」。

## 7. 外部與內部介面

- **使用者**：做裁定、釐清不明內容、回答待裁定問題、驗收；讀 roadmap 與待裁定清單。
- **git**：可能有多個 repo，工作區本身也可能沒有 git。任務的檔案與證據要帶上 repo 與 commit。
- **測試執行**：跑測試並把結果寫成證據紀錄，包含指令、commit、環境、通過／略過／失敗數。
- **LLM 審查**：輸入是文件與寫作規範；輸出是待處置的發現。
- **agent**：所有讀寫都透過指令；防護只擋寫入。
- **治理層 ↔ 兩個領域**：以編號互相引用。
- **文件領域 ↔ 軟體領域**：雙向。文件可以描述軟體；某些文件（例如資料格式規範）也可能是軟體需求的依據。

## 8. 運作流程（生命週期）

1. agent 發現需要使用者決定的事，建立待裁定問題。
2. 使用者回答，清楚就保存原話、轉記成生效裁定；只有不清楚才先覆述等確認。提供現況事實則記為資訊。
3. 依裁定新增決策，或寫出完整新版取代舊決策。
4. 影響分析把受影響的需求、任務、測試、文件章節標為可疑。
5. 開啟軟體 change 或文件 change 來處理，沿用或登記 roadmap 工作並連到實際工作。
6. 實作並產生有型別的證據（驗證）。
7. 使用者驗收（確認）。
8. 封存，形成新基線；引用內容變動時依規則標示相關文件需更新。文件與軟體的差異不互相阻擋定版／封存。
9. Roadmap 查詢時推導現況；交棒前整份重寫 handover，保留承諾、注意事項與下一步。

設計原則：

- 紀錄是權威，文字是檢視。
- 現況由紀錄推導；交接單整份覆寫。治理取代關係與封存歷史保留，不把交接單當成追加歷史。
- 兩個領域各有自己的結構，不互相套用。
- 依各領域的完成條件阻擋結構、失效依據與證據錯誤；追溯缺漏及跨領域差異只提醒。可疑標記須審閱處置，不由 agent 直接忽略。
- 使用者是唯一的最終權威；工具檢查已記錄依據的效力與追溯，但無法保證 agent 轉記的原話真實性。

## 9. 分期與關卡

工作規則（2026/09/29 裁定）：每一期開始前，該期的架構要經使用者確認（架構關卡）；每一期結束時，該期的驗收情境要全部通過，並經使用者確認（驗收關卡）。

- **第零期（架構關卡已通過）**：系統需求與架構第二版；使用者已確認本檔第 4、5 節，後續修訂依裁定紀錄。
- **第一期：治理層＋追溯（已驗收）。**
  - 範圍：待裁定問題、裁定（原話與必要釐清）、資訊、決策（完整新版）、唯一 roadmap、一筆一檔的紀錄儲存、追溯圖、影響分析與可疑標記、文件章節依賴治理紀錄、待裁定清單、文件審查發現的處置狀態，以及防護只擋寫入等小修正。
  - 驗收情境：S1、S2（治理層＋文件部分）、S3、S4。
- **第二期：軟體領域（取代 OpenSpec，已驗收）。**
  - 範圍：能力規格、軟體 change、任務、證據紀錄、驗證與確認、專案基線、OpenSpec 功能對等、OpenSpec 匯入。
  - 驗收情境：S2（完整）、S5。
- **第三期：遷移與接手改善（範圍已縮小）。**
  - 範圍：既有 docspec 專案遷移細節留待架構關卡；接手使用既有環境檢查、roadmap 與每次整份重寫的 handover。取消產品多 agent 寫入權、測試埠協調、多人編輯與交接歷史。
  - 驗收：S6 取消。接手改善以 S4 與合成 E11 驗證，分開記錄流程缺陷與 agent 表現。工作摘要已以 `add-work-summary` 實作；`complete-cross-platform-validation` 本輪 Windows／Linux 最終完整回歸各 1433 passed、1 skipped，PDF／proof 各 83 passed、0 skipped，正常／過時四案通過獨立核對。Linux 接手為全新 Windows controller 經 WSL 操作 Linux runtime；未測 Linux 原生 controller，線上字型 ZIP 校驗失敗與離線復原均保留於 [驗證報告](validation/work-summary-run.md)。不以本機結果代稱遠端 CI 通過。全新 agent 實測在流程修改或發布前由人啟動，CI 只做機械回歸。

## 10. 驗收情境（保留原案例背景，新回歸與 E11 使用合成資料）

- **S1 目前有效設計（第一期）**：以 D13、D15 為來源寫出 D7 的完整新版後，「目前有效設計」只出現新版。歷史可以查到 D7 原文、D13、D15，以及它們依據的裁定。
- **S2 影響分析**：取代「/tasks 頁面維持不變」這條決策時，系統把下列項目全部標為可疑：
  - 已封存舊規格裡的需求「第一列任務在第一畫面」；
  - 已完成的任務 6.6（標記重看，不重開）；
  - 驗收它的瀏覽器測試（test_entry_page.py）；
  - 說明書的相關章節。

  每個標記附理由清除後才會消失。第一期只驗證決策 → 文件章節這一段；第二期驗證完整鏈。
- **S3 裁定記錄與效力（第一期，依現行裁定修訂）**：使用者明確決定的內容，轉記時保存原話、不必另外覆述確認即可生效；不清楚的內容先釐清。使用者事後駁回裁定，依據它的決策不能繼續被當作有效依據；工具不宣稱能驗證原話出自本人。
