# 第二期設計 review（2026/09/30）

- 範圍：第二期全部實作（`docspec code …`、證據、封存、治理層連結、OpenSpec 匯入、skill）。
- 方法：系統工程觀點看架構，並在暫存區的示範專案實際「攻擊」每個把關機制；以下每一項都已實測重現，除非特別註明。
- 結論：架構方向正確，但「以證據判定完成」這個核心機制有 6 個可以繞過的洞，第二期驗收關卡應延到修好之後。

## A. 證據可信度（核心機制）

### A1 任意指令冒充測試（嚴重）

- 實測：測試檔是 `assert False`，執行 `docspec code evidence run f 1 -- true`，任務變成「完成」。
- 原因：`--` 後面可放任意指令；不是 pytest 時只記一則「無逐項結果」提醒，沒有判為不通過。
- 修法選項：
  - 甲：取消 `--`。一律由引擎組指令：repo 設定的執行器 ＋ 規劃測試的完整位置 ＋ JUnit 報告。執行器必須能產出 JUnit（pytest、jest-junit、go-junit-report、ctest 都可以）；不能產出的，改用檢查／分析類證據。
  - 乙：保留 `--`，但它跑出的結果只當參考，不能讓任務完成。
- 建議：甲。

### A2 同名測試檔冒充（嚴重）

- 實測：另建一個永遠通過的 `fake/tests/test_a.py`，用 `--rootdir=fake` 執行，引擎把它當成規劃的 `tests/test_a.py`，任務變成「完成」。
- 原因：為了容忍 pytest 根目錄不同，比對只看路徑尾段。
- 修法：引擎組指令時固定 `--rootdir=<repo 根目錄>`，比對改為完整路徑精確相符。
- 要驗證：台中港 labelvault 若有自己的 pytest 設定檔在子目錄，固定根目錄後測試仍要能正常收集。

### A3 實作者改測試檔（嚴重，新發現）

- 實測：測試是 `assert False`，實作者把它改成 `assert True`（沒宣告這個檔案），任務變成「完成」。
- 原因：證據只記錄「跑的當下」檔案內容；沒有記錄「測試角色寫好的版本」，所以測試被誰改過都不知道。
- 修法：新增「測試角色簽收」`docspec code testplan sign <change> [T…]`。測試角色寫完測試後簽收，引擎記下測試檔與測試設定檔（見 A4）的內容指紋與簽收者。之後跑證據時，只要這些檔案和簽收版本不同就判不通過：「測試在簽收後被改過」。測試角色改測試要重新簽收，留下紀錄。實作任務宣告測試檔從提醒改為錯誤。

### A4 改 conftest.py 或測試設定讓失敗變通過（嚴重，新發現）

- 實測：不動測試檔，只加一個 `tests/conftest.py`，把所有結果改報成通過，任務變成「完成」。
- 原因：同 A3，測試的「環境」也沒被保護。
- 修法：A3 的簽收範圍包含測試檔所在目錄一路到 repo 根目錄的 `conftest.py`，以及 pytest 設定（`pytest.ini`、`setup.cfg` 的 `[tool:pytest]`、`tox.ini` 的 `[pytest]`、`pyproject.toml` 的 `[tool.pytest.ini_options]`）。只取 pytest 相關的段落，避免改個相依套件就要重新簽收。
- 剩下擋不住的：透過已安裝的 pytest 外掛或程式碼偵測「正在測試」而作弊。這類只能靠驗證時的語意審查與 CI 獨立重跑（見 D3）。

### A5 任務不宣告檔案，證據永不過期（中等）

- 實測：可以新增一個以測試驗證、卻沒宣告任何檔案的任務。
- 後果：之後改程式不會讓它退回「需重跑證據」。只有測試檔本身變了才會。
- 修法：以測試驗證的實作任務必須宣告至少一個檔案，允許宣告整個目錄（例如 `labelvault:src/portal/`，目錄內任何檔案變動都算）。

### A6 豁免可以引用無關的裁定（中等）

- 實測：記一條「首頁字型用思源黑體」的裁定，拿它豁免一個測試任務，任務變成「完成（含豁免）」。
- 原因：只檢查裁定存在且有效，沒檢查裁定和這個任務有關。
- 修法選項：
  - 甲：裁定記錄時要指明對象（`docspec ruling add … --about swc:<change>#<任務>`），豁免只接受指向這個任務的裁定。
  - 乙：豁免本身走覆述確認（agent 覆述要豁免什麼、你回覆確認），不需要另一條裁定。
  - 丙：維持現狀，但在驗證、一頁現況、封存輸出中把裁定原文和被豁免的任務並列，讓人一眼看出不相干。
- 建議：甲＋丙。需要使用者決定。

## B. 可用性

### B1 封條錯誤訊息誤導（小）

手改軟體檔時，訊息建議 `docspec store fsck --accept`，但那個指令不處理軟體檔。修法：改訊息，說明只能透過 `docspec code …` 改，不提供「接受手改」。

### B2 匯入後補連結工作量大（中等）

台中港 dataset-library 匯入後，有 46 條需求沒有任務對應、111 個情境沒有測試規劃，目前只能逐條下指令。修法：`docspec code change gaps <change> --template` 輸出一份列好缺口的 YAML 草稿；agent 填好後用 `task set --from` 和 `testplan add --from` 一次寫入，引擎照樣逐條驗證。

### B3 匯入時驗證方法一律設為 test（中等）

OpenSpec 沒有這個欄位。畫面、版面類需求被當成「要自動化測試」，封存時會要求測試規劃。影響範圍：只有被 change 改到的需求會受檢查，不是全部 105 條。修法選項：甲，維持 test，報告列出看起來像畫面類的需求供人判斷；乙，匯入時標為「未定」，改到它的 change 必須先指定驗證方法。建議甲。

### B4 「同一個 agent 寫測試又跑測試」提醒會誤報（小）

目前比的是「測試撰寫者」和「跑證據的人」。測試角色自己跑測試是正常的，卻會被提醒。修法：任務記錄建立者，改比「測試撰寫者」和「任務建立者／宣告檔案的人」。

## C. 多分支並行（第三期範圍，已實測）

### C1 同一個 change 在兩個分支各加任務會衝突

- 實測：兩個分支都新增「任務 7」，合併時 `tasks.yaml` 衝突；而且它是封條檔，手動合併會破壞封條。
- 修法方向：每個任務一個檔、編號帶工具前綴（與治理層相同），或提供合併工具重新編號。第三期決定。

### C2 證據編號撞號

- 實測：兩個分支都產生 `E-claude-9`，合併時同名檔衝突。
- 修法方向：與治理層編號同一套處理（第三期 S6）。

## D. 已知、接受的風險

### D1 身分只靠工具名稱

`--by gemini` 或環境變數就能冒充測試角色。引擎記錄、提醒，但無法強制。

### D2 驗收確認的真實性

`--confirmed` 的文字由 agent 寫入，程式無法證明出自使用者。與第一期「對話中覆述確認」相同，以紀錄可見性與事後駁回因應。

### D3 繞過指令直接呼叫引擎

- 實測：用 Python 直接呼叫引擎把任務改成「完成」，下一次 `change status` 就被引擎依證據改回。
- 但同樣手法可以直接寫一筆假的證據檔：封條是內容雜湊，不是密碼學簽章，同一台機器上的 agent 拿得到全部程式。
- 封條的作用是防「不小心手改」，不是防「刻意偽造」。
- 真正的防線是獨立重跑。可以選擇封存前由引擎重跑所有規劃測試；也可以由 CI 跑 `docspec code test`，CI 的環境 agent 碰不到。
- 需要使用者決定：封存時要不要強制重跑（代價是真模型、瀏覽器測試耗時）。

### D4 程式偵測測試環境而作弊

例如程式裡寫「在測試中就回傳預期值」。任何工具都擋不住，只能靠 dspx-verify 的語意審查（換一個 agent 看程式與測試）。

## E. 文件與效能

- `phase2-detail.md` 經多次修訂：第 15 節取代第 1、3、5、9、11 節的一部分，讀者容易混淆。修法：整理成一份「現行版」，舊內容移到附錄。
- 效能：以台中港匯入後的規模量測，`check` 約 3.1 秒、`brief` 約 0.9 秒、`change status` 約 1.9 秒、`roadmap` 約 0.4 秒，可以接受。
