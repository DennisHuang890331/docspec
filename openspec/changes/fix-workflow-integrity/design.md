## Context

review 對 `5a942b6` 的十個合成情境已重現：漏執行必要測試仍封存、最新零測試失敗被忽略、情境變更沿用舊證據、同檔改測試位置仍完成、駁回豁免仍有效、過期使用者驗收仍放行、提案不能先建測試型任務、roadmap 手動結案蓋過未完成連結、駁回決策依據未擋相關軟體封存、文件舊定版使新內容誤報完成。

既有 11 個相關測試檔在本次 Windows 環境得到 131 passed、2 failed；兩個失敗分別涉及執行器路徑反斜線解析及路徑分隔符斷言。不是完整測試結果。roadmap 文字資訊、開工登記、交接新鮮度及過時規範另經程式與 skill 檢視確認。

現行核心以 `software/evidence.py` 推導任務狀態、`software/archive.py` 判斷封存；`roadmap_v2.py` 另行推導工作狀態。新鮮度主要依宣告檔案雜湊；`handover.py` 目前只記日期。修正以共用查核結果消除這些入口間的不同判準。

## Goals / Non-Goals

**Goals:**

- 同一組有效性判斷用於任務查詢、封存與 roadmap，讓使用者能追查未完成原因。
- 只使相關工作失效；錯誤訊息給出補連結、重新簽收、重跑證據或重新驗收的下一步。
- 保持封條紀錄與封存歷史可讀；新增驗證範圍資料，不重新建整套儲存架構。
- 用會抓到實際錯誤的合成情境驗收，包含正向通過案例與跨平台案例。

**Non-Goals:**

- 不防 agent 刻意偽造身分、直接呼叫引擎或改測試環境作弊；延續已接受風險。
- 不新增多人或多 agent 並行、鎖、分支合併機制。
- 不讓文件與軟體互相阻擋、不把缺少治理連結一律升為錯誤。
- 不自動推論豁免重啟條件或裁定原話是否語意相關；保留原話並列與人工審查。
- 不要求封存時再完整重跑全部測試，不擴大為自動監控所有外部 repo 內容。
- E11 全新 agent 實測不在本次自動執行清單內；先準備 S4 與機械式接手驗收。

## Decisions

### 1. 先決定必須驗證什麼，再判斷有哪些有效證據

由套用差異後的需求與情境產生必要驗證集合。新增／修改情境納入集合；需求 statement 改變時納入其現有情境；純標題改名不重跑所有情境。測試型需求必須有測試型實作任務，或明確適用的有效豁免。每個必要情境須有規劃測試；凡規劃為驗證該情境的測試，都必須被相關實作任務引用，並有有效證據或其任務豁免。

共享測試允許驗證多個情境，不要求重複跑相同測試。封存沿「情境 → 計畫 → 相關任務 → 有效證據」檢查，不能用 unrelated task 的成功代替。`verified-by` 只列真正通過的測試；豁免保存在基線與任務紀錄，不把未執行的測試寫成已驗證。

替代方案是封存前重跑所有測試，但既有裁定不採強制重跑；完整追查現有證據即可修補此缺口。單純要求測試計畫存在仍會漏掉執行，故不採。

### 2. 新證據記錄局部的驗證範圍，舊證據明示不足

新增有版本的驗證範圍資料及指紋，內容包括：

- 任務實作的需求規範句、驗證方法、情境 WHEN／THEN，以及直接治理依據。
- 任務驗證方法、計畫測試 id／位置／covers、allow-skips 與宣告檔案清單。
- 該任務測試執行器的相關設定。檔案內容仍沿用既有 snapshot 機制。

只取任務依賴的內容，不以整份 change 或整個 governance 目錄的雜湊使所有證據一起失效。呈現文字、非行為標題、日期等不作為行為變更的替代品。signoff 在既有 test-fingerprint 外新增其涵蓋情境的行為指紋；改情境或 covers 後要重新簽收。

同一任務、同一驗證方法先取最新一次嘗試，再檢查結果、必要測試覆蓋、範圍指紋、簽收與檔案新鮮度。失敗或收集不全不能在選取前被丟掉。沿用現有證據時序，不新增跨 agent 並行排序機制。

進行中工作缺少新範圍資料時顯示「舊證據未記錄驗證範圍，需補驗證」；舊簽收缺少情境指紋時提示重新審閱簽收。不能在讀取舊證據時用目前需求回填。舊封存歷史維持原樣。

### 3. 裁定效力和完成證據分開檢查

共用授權有效性判斷供查詢、豁免與封存使用：豁免引用的裁定須仍 effective；決策的依據不得缺失或被駁回。一般裁定被新裁定取代時沿用既有「需審閱／取代決策」流程，不額外把所有歷史依據一律改判駁回；豁免則依原有須引用目前有效裁定的規則重新判斷。

影響分析循已記錄依據與實作／驗證連結傳到相關工作；已封存任務只標需重看。軟體封存還要直接驗證該 change 所依據決策的效力，不能只靠可手動清除的 suspect。治理層有無關錯誤不作為此 change 的全域封存閘。

新豁免保存其任務範圍；範圍改變或裁定失效後，先嘗試其他有效完成證據，不再讓歷史 waiver 永遠優先。尚有效且仍適用的豁免照原規則顯示完成含豁免。

使用者驗收另以目前需求、任務範圍與檔案內容檢查，不能使用「有過 acceptance 即通過」。檢查型任務的技術驗證可以完成，但缺目前版本的使用者驗收時封存仍列出缺口。驗收覆蓋需求的相關實作範圍，避免某一個小任務的驗收代表同需求其他已修改內容。

### 4. roadmap 沿用完成狀態，補上完成依據與說明

`roadmap done` 拒絕有可推導完成條件或子項目的工作；僅有 gov:D 約束連結不算完成條件。已有 closed 紀錄的項目後來新增連結或子項目時，保留歷史但以當前條件推導，不讓 closed 永遠優先。

整份文件交付結合既有同步狀態及 `project_baseline` 的目前內容／定版快照比對。章節寫作與文件交付分開：章節可已寫好，整份文件仍未定版。單獨 stale-software 不把已定版文件退回未完成；另列非阻擋差異提醒。

保留既有 status 值，新增或補齊詳細原因欄位；文字與 JSON 使用同一份資料。軟體摘要讀取現有任務證據解釋與計畫缺口，查詢不代跑測試、不新增證據。既有完成歷史的需重看提示獨立呈現。

替代方案只補文字輸出，無法修正 closed 與曾定版的誤判，故須同時修推導。

### 5. 讓提案交棒發生在測試規劃之前

允許 `task add --verify test` 暫無 tests；任務保留 not-started，原因顯示待測試規劃。提案的非嚴格檢查將「尚無測試計畫／任務連結」列為待交棒事項，其他格式、死引用等錯誤仍照原規則處理。嚴格封存檢查與 evidence run 要求必要計畫完整。

不要求先虛構 T-id，也不把任務暫設 analysis 以繞過檢查。提案 skill 的「修完每個錯誤才交棒」改成區分不可交棒的結構錯誤與交給測試角色的待辦。測試規劃完成後再進入實作，角色以順序交接運作。

產生的 AGENTS.md 與 skills 同步要求先找既有 roadmap 工作、缺少才新增；開工登記屬流程規範，不新增無連結封存阻擋。統一現行覆述規則、移除 brief／govern 與並行寫入指示，保留既有測試異議與審查分工。

### 6. 交接單比較內容狀態，不靠日期或檔案時間

寫交接單時保存目前紀錄的狀態指紋與帶時區時間。指紋取治理紀錄（排除 handover 自身）、roadmap、軟體規格／進行中 change／證據、文件來源與受管理工作文字、ledger／定版資訊及文件 change。內容採穩定排序；生成 PDF、暫存預覽、快取與單純檔案 mtime 不納入。

讀取時重新比較，不同即非阻擋提示；舊交接單缺指紋時明示未知。內容不可讀時提示不能確認，不能吞掉錯誤宣稱最新。讀取不重寫交接單也不刷新其他紀錄，避免讀一次就把自己弄過時。

這只說明受管理紀錄是否改變，不宣稱已偵測所有外部程式或環境變化。日期-only 方案辨識不了同一天的事件，mtime 方案容易受搬檔或 checkout 影響，因此不採。

### 7. Windows 指令解析維持現有設定介面

以平台相容的參數解析保留 Windows 反斜線與雙引號包住的執行器路徑；支援現有測試資料使用的 POSIX 引號形式。環境變數前綴仍由引擎帶入，不改為 shell 執行。無引號且含空白的可執行檔路徑視為格式不明，明確提示加引號，不猜測哪一段是檔名。

先用原生 Windows 路徑、含空白路徑、環境變數與 POSIX 引號測試固定契約，再選擇最小解析修正。路徑顯示測試用 Path 或規範化比對，不只為了測試通過改動產品輸出分隔符。

## Risks / Trade-offs

- [舊的進行中證據需補簽與重跑] → 明確提示原因與操作，不自動代跑；已封存歷史不受影響。
- [驗證範圍太寬導致過度重驗] → 使用任務局部內容，加入不相關需求變更仍有效的正向案例。
- [影響傳遞過度阻擋] → 只檢查已有依據鏈，加入無關 change、文件獨立定版、已封存只標需重看的案例。
- [交接指紋讀取成本] → 共用本次查詢已讀入資料，排除匯出與暫存檔；用合成多文件資料確認查詢不觸發昂貴操作。
- [Windows 與 POSIX 引號差異] → 保留兩種平台回歸案例，無法在本機執行的平台明說未實跑，不以模擬替代原生驗證。

## Migration Plan

1. 負責人審閱本提案，核定後將具體裁定記入 `docs/dev/system-design.md`，再開始 apply。
2. 先將十個已重現情境改寫成期待正確行為的失敗測試，使用 repo 內可攜合成 fixtures；每個修復群組同時補正向案例與說明。
3. 新寫入證據／簽收／交接單帶上版本資料；舊格式仍可讀，僅進行中證據按新有效性規則提示補驗證，不批次改寫。
4. 更新現行設計、CHANGELOG 與 S4：交接單加 roadmap 能解釋狀態與下一步。專案規範仍由使用者重跑 init --agents-md 更新。
5. 跑相關測試、完整測試及 OpenSpec 驗證，分別回報實際結果。未實施 E11 就明示未實施。
6. 回退採程式版本回退並保留新增紀錄；不刪新證據或對舊歷史重新封條。支援的新欄位僅增加在既有可擴充紀錄處；嚴格 schema／封條相容性納入回歸測試，避免回退後無法讀取。
